# 案例：DSH 插件在 web profile 下 spawn provider 未注册

**日期**：2026-09-23
**环境**：Windows 11 + PowerShell 5.1 + pnpm 12 + DSH 0.1.5-rc.2
**插件**：`dsh-agent-weave@0.1.0`（自研）
**最终状态**：已修复并验证通过


## 一、症状

### 主症状

`weave-test`（web 全量 profile）启动时：

```
{"level":"error","component":"weave","msg":"找不到底层 subagent provider，跳过角色注册（图命令不受影响）","data":{"base_provider":"spawn"}}
```

同一插件在 `weave-headless`（headless profile）下**正常**，6 个角色全部注册成功。

### 伴随症状

- 三件套 `Test-Path` 全部 `True`（`dsh-subagent` / `dsh-subagent-spawn-in-process` / `dsh-subagent-in-process-driver`）
- `--dump-config` 显示 spawn 插件**在配置树里**
- 完整启动日志**没有** spawn 插件的加载痕迹（成功或失败都没有）
- 报错行号始终是 `lib/index.js:51:74`，即使换了新 tgz 也不变


## 二、根因（两层）

### 根因 1：插件源码的加载时序竞态（核心）

`dsh-agent-weave` 的 `apply` 函数**同步**取 provider：

```ts
const delegate = ctx.subagents.getProvider(config.baseProvider ?? 'spawn')
if (delegate !== undefined) { /* 注册角色 */ }
else { /* 报错 */ }
```

**Cordis 加载器并发启动所有 entry**。`spawn` 插件和 `weave` 插件同时 apply：

- **headless**：加载链短（dsh-base + dsh-headless），spawn 恰好在 weave 之前跑完 → 成功
- **web**：dsh-web-app 要加载大量 Web 插件，spawn 被拖慢 → weave 先跑 → `getProvider` 返回 `undefined`

**这是插件源码的 bug，不是环境配置问题。**

### 根因 2：pnpm 对 `file:` 依赖的缓存策略（阻碍修复生效）

pnpm 的 `.pnpm/dsh-agent-weave@file+..+.._b676a8c2...` 这个 hash 目录名，**是基于路径算的，不是基于内容**。

即使 tgz 内容变了，只要路径不变，hash 就不变，pnpm 认为"没变化"，继续用旧缓存。

**结果**：源码改了、重新打包了、tgz 里确实是新代码，但 profile 里装的还是旧的。


## 三、正确修复步骤

### 步骤 1：改插件源码

修改 `src/index.ts` 的 `apply`，把同步单次判断改成**同步试一次 + 轮询等待**：

```ts
const tryRegisterRoles = (): boolean => {
  const delegate = ctx.subagents.getProvider(baseProviderName)
  if (delegate === undefined) return false
  // ... 注册角色
  return true
}

if (!tryRegisterRoles()) {
  let attempts = 0
  const maxAttempts = 50
  const timer = setInterval(() => {
    attempts++
    if (tryRegisterRoles() || attempts >= maxAttempts) {
      clearInterval(timer)
      if (attempts >= maxAttempts) {
        logger.error('weave', '等待 spawn provider 超时，跳过角色注册', new Error('spawn provider 未注册'), {
          base_provider: baseProviderName,
        })
      }
    }
  }, 100)
  ctx.effect(() => () => clearInterval(timer))
}
```

### 步骤 2：重新构建 + 打包 + 手动移到 dist

```powershell
cd <WEAVE_SRC>
Remove-Item -Recurse -Force .\dist -ErrorAction SilentlyContinue
Remove-Item -Force .\*.tgz -ErrorAction SilentlyContinue
pnpm install
pnpm build
pnpm pack
Copy-Item .\dsh-agent-weave-0.1.0.tgz "D:\...\3pluginCode\dist\" -Force
```

> **注意**：`pnpm pack` 只输出到当前目录，`dist/` 是手动拷贝的。

### 步骤 3：彻底清 pnpm 缓存（关键！）

```powershell
cd <TEST_HOME>\profiles\weave-test

Remove-Item -Recurse -Force ".\node_modules\dsh-agent-weave" -ErrorAction SilentlyContinue
Remove-Item -Recurse -Force ".\node_modules\.pnpm\dsh-agent-weave*" -ErrorAction SilentlyContinue

pnpm store prune
pnpm add "file:D:/.../dist/dsh-agent-weave-0.1.0.tgz"

# 验证：必须看到 tryRegisterRoles
Select-String -Path ".\node_modules\dsh-agent-weave\lib\index.js" -Pattern "tryRegisterRoles|setInterval"
```

**不做这一步，pnpm 会继续用旧缓存，修复永远不生效。**

### 步骤 4：两个 profile 都要重装

`weave-test` 和 `weave-headless` 的 `node_modules` 独立，必须**各装一遍**。

### 步骤 5：验证

```powershell
cd <PROJECT_ROOT>
$env:DSH_HOME = "<TEST_HOME>"
$dshBin = "$env:USERPROFILE\.dsh\profiles\node_modules\@deepseek-ai\dsh\lib\bin.js"

node $dshBin --profile weave-test --port 3081 2>&1 | Select-String -Pattern "注册角色|找不到底层|图引擎|超时"
```

**预期**：6 行 `注册角色 R1-requirement ...`，无 `找不到底层`，无 `超时`。


## 四、踩坑汇总

### 坑 1：把 spawn 未注册错归因到 pnpm 构建问题

**错误假设**：`ERR_PNPM_IGNORED_BUILDS` → spawn 依赖 native 模块 → 所以 spawn 没注册。

**实际**：`spawn-in-process` 是纯 JS 进程内实现，不需要编译 native 模块。`IGNORED_BUILDS` 是另一个独立问题，修了也不会让 spawn 注册。

### 坑 2：手动给 patch 加 insert，导致 duplicate loader entry id

```yaml
- insert:
    - id: subagent-spawn-in-process
      name: '@deepseek-ai/dsh-subagent-spawn-in-process'
```

报错：`duplicate loader entry id: subagent-spawn-in-process`。

**原因**：bundle 层**已经包含** spawn 的 insert，手动再加就重复了。`--dump-config` 有它，说明配置层没问题，问题在**运行时加载时序**。

### 坑 3：PowerShell 5.1 的 `Set-Content -Encoding UTF8` 写 BOM

导致：
- `pnpm install` → `Invalid package.json`
- `pnpm add` → `Failed to parse pnpm-workspace.yaml: a BOM must not appear`

**正确写法**（永远用这个）：

```powershell
$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText("绝对路径", $内容, $utf8NoBom)
```

### 坑 4：`[System.IO.File]::ReadAllBytes(".\package.json")` 解析到错误路径

.NET 方法的相对路径基于**进程当前目录**（通常是 `C:\Users\<用户名>`），不是 PowerShell 的 `$PWD`。

**必须用** `(Resolve-Path ".\package.json").Path` 转绝对路径。

### 坑 5：pnpm 对 `file:` 依赖的 hash 基于路径，不基于内容

改源码、重新打包，pnpm 依然用旧缓存。**必须删 `.pnpm/dsh-agent-weave*` 目录 + `pnpm store prune`。**


## 五、通用经验教训

### 1. 区分"没装"、"没加载"、"加载了但没注册"

| 症状 | 排查方向 |
| :--- | :--- |
| `Test-Path` 为 `False` | 包没装 |
| `--dump-config` 没有 | 配置层没加载 |
| `--dump-config` 有，运行时无日志 | 时序问题（并发加载） |
| 运行时日志有 error | 注册失败（源码 bug 或依赖缺失） |

### 2. 插件源码的同步依赖要改成延迟重试

Cordis 并发加载所有 entry，任何在 `apply` 里**同步取另一个 provider** 的代码，都是竞态 bug。正确做法：

- `ctx.inject([...], ctx => { ... })` 延迟到服务可用
- 或轮询重试（如本案例）
- 或惰性查找（第一次调用时再取）

### 3. pnpm `file:` 依赖必须清缓存

`file:` 依赖的 hash 只跟路径相关，内容变化不刷新缓存。改 tgz 后必须：

```powershell
Remove-Item -Recurse -Force ".\node_modules\.pnpm\<包名>*"
pnpm store prune
pnpm install --force
```

### 4. PowerShell 5.1 的编码陷阱

- `Set-Content -Encoding UTF8` **一定带 BOM**
- .NET 的静态方法用**进程当前目录**，不是 `$PWD`
- 写 JSON/YAML 统一用 `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`

### 5. 两个 profile 的 node_modules 独立

给 `headless` 装的包，`test` 不会自动有。**两边都要装。**

### 6. 排查效率

- **一次只验一个假设**，避免一次跑一堆命令
- `--dump-config` 是判断"配置层 vs 运行时"的最快手段
- 完整启动日志比 grep 更有价值，容易被过滤掉的信息往往才是根因


## 六、下次遇到类似问题的检查清单

1. `--dump-config` 有目标插件吗？
   - 没有 → 查配置层（bundle、patch）
   - 有 → 继续
2. 完整启动日志有目标插件的加载痕迹吗？
   - 没有 → 时序问题，检查 `apply` 是否同步取其他 provider
   - 有 error → 查具体错误
3. 包版本正确吗？
   - `Select-String -Path ".\node_modules\<包名>\lib\index.js" -Pattern "<新代码关键字>"`
   - 没有新代码 → pnpm 缓存问题，清 `.pnpm` + `store prune`
4. 两个 profile 都装了吗？

---

**沉淀结论**：DSH 插件开发中，**"同步取另一个 provider"是反模式**，必须改成延迟重试。同时，Windows + pnpm `file:` 依赖的缓存策略会掩盖修复效果，排查时要先确认"profile 里装的确实是新代码"，再分析运行时行为。
