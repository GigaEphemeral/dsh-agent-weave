# MVP-1 实现逻辑总览

> 版本：v1（2026-09-22）｜目标读者：开发者/维护者
> 目标：说清楚「角色 YAML → 可执行协作链」这一条 MVP-1 主线的实现逻辑与关键决策

## 一、主线架构

```
角色 YAML (roles/*.yaml) + skill 文件 (skills/*/SKILL.md)
        │ ① Zod 校验（role-schema.ts）
        ▼
RoleDefinition（纯数据）
        │ ② 编译（role-loader.ts：读 skill、路径逃逸校验、字段映射）
        ▼
RoleProfile → ③ 包装为 SubagentProvider（start() 注入 persona/toolFilter/agentOptions → 委托 spawn）
        │ ④ 注册到 ctx.subagents（src/index.ts apply）
        ▼
SubagentProvider[]（6 个角色 provider，插件卸载自动撤销）
        │ ⑤ 触发（weave:run-chain 工具 → chain-runner.ts）
        ▼
runChain() 串行调用 ctx.subagents.start(角色ID, request)
        │ ⑥ 每步：角色独立 Session（记忆隔离）→ 产物落盘 productions/<角色ID>/
        ▼
R1→R2→R4→R6→R7→R8 六阶段交付物
```

## 三、关键契约与决策（D-001）

### 3.1 SubagentProvider 官方契约（与设计文档的偏差）

设计文档假设 `SubagentProvider` 的 `capabilities` 携带 `persona/toolFilter/agentOptions` 值；
**官方 0.1.5-rc.2 实际是**：

```typescript
interface SubagentProvider {
  name: string;
  capabilities: SubagentCapabilities;   // 布尔标志：agentOptions/outputSchema/depthLimit/toolFilter/persona
  inheritsParentContext: boolean;        // 描述性，非服务校验
  agentRouteDefaults?: { provider, model };
  start(request: ResolvedSubagentStartRequest): Promise<SubagentRun>;  // 必需
  prepareContinuable?(...): ...;         // 可选
}
```

- `persona` / `toolFilter` / `agentOptions` / `maxDepth` 属于 **`SubagentStartRequest`**（每次 start 传入）
- 因此角色以「**包装 provider**」存在：`start()` 在请求中注入角色字段后委托给底层 `spawn` provider

### 3.2 workflowEngine 无法按角色选择 provider

官方 `dsh-workflow-worker-thread` 的 `agent(prompt, opts)` 仅支持
`{label, phase, schema, provider, model}`，其中 `provider` 是 **LLM 路由覆盖**
（进入 `agentOptions.provider`），**不是** `ctx.subagents.start(name)` 的 provider 选择。

→ MVP-1 单链改为**自写编排**（`chain-runner`）+ `weave:run-chain` 工具触发，
不依赖 workflowEngine 的按角色切 provider。

### 3.3 模型路由 🐛

- `llm-pi-ai` 用**模型 ID**（`DeepSeek-V4-Flash`）做解析键，**非 name**（`deepseek-v4-flash`）
- 角色 YAML 的 `model.model` 必须写 ID：`DeepSeek-V4-Flash`（token 消耗小的 flash）

### 3.4 路径解析

- `rolesDir` / `skillsDir` 默认基于**插件包根**（`import.meta.url`），不依赖 `process.cwd()`
- `system_prompt_ref` 相对路径基于 skillsDir 解析；编译期校验路径不逃逸 skillsDir

## 四、记忆隔离与 toolFilter 的实现

| 机制 | 实现 | 验证 |
|---|---|---|
| 记忆隔离（G4） | 角色 provider `inheritsParentContext: false` + spawn 每次全新 session | 6 子代理独立 session 文件 + 各带独立首条 prompt |
| toolFilter | 角色 provider `start()` 注入 `toolFilter: { allow: [...role.tools] }` | 官方 `applyChildComposition` → `childCtx.tools.restrict()` |
| 上游交接 | 下游 prompt 只携带上游「摘要 + 文件路径」 | chain 日志 `upstream_count` 0→5 递增 |

## 五、与后续 MVP 的衔接

| MVP-1 产出 | MVP-2 如何使用 |
|---|---|
| `compileRoleToProvider`（SubagentProvider 包装） | StateGraph 节点通过 `roleRef` 引用已注册角色 |
| `RoleDefinitionSchema` | 图 DSL 的 `roleRef` 指向角色 id |
| `chain-runner` 产物落盘 | `art://` 工件引用基于 `productions/<角色ID>/` |
| 记忆隔离验证 | 节点执行继续复用 `inheritsParentContext=false` |
| `weave:run-chain` 工具 | 由 StateGraph 引擎取代（MVP-2 质变点） |
