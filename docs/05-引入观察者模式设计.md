# 可视化 Agent 任务编排工具 · 观察者机制设计文档

> 版本：v1（2026-09-22）｜基于整体设计 v4，新增**观察者机制**作为正交增强层
> 定位：在现有 StateGraph 编排引擎、质量门、RunLedger 基础上，引入**并发观察者**模式，实现“节点执行过程中发现偏离”的能力
> 来源：PACT 并发审计协议、AgentOS 跨代理护栏接口、Hankweave Sentinel 执行模型、Observer Pattern 学术综述


## 一、观察者机制定位

### 1.1 为什么需要观察者

现有设计中，质量审核（R8）是**节点完成后的质量门**——开发节点全部完成后，才由质量审核节点判定是否通过。这存在两个问题：

- **发现偏离太晚**：架构漂移在开发过程中逐步累积，等到节点完成后再审核，返工成本已被放大。PACT 的并发审计协议明确指出，“纯事后审查（TEST 阶段）的多样性低于并发观察”。
- **循环回退代价高**：当前“开发→测试→审核→回退→再开发”的循环中，每次回退都意味着质量审核节点生成反馈、开发节点重新读取反馈和原上下文、测试节点重新读取更新后的代码，Token 消耗可能是单次通过的 5-8 倍。

**观察者机制补的是“在节点执行过程中发现偏离”这一能力**，与质量审核节点形成互补而非替代。PACT 的表述很精确：“审计者补充而非替代 TEST 阶段和同行评审”。

### 1.2 观察者与现有机制的关系

| 机制 | 触发时机 | 介入方式 | 与观察者的关系 |
|---|---|---|---|
| **质量审核节点（R8）** | 节点完成后 | 完整 LLM 审查，输出通过/不通过 | 观察者是其**前置预警层** |
| **质量门（Quality Gate）** | 阶段边界 | 检查清单，可量化标准 | 观察者是其**过程监控层** |
| **RunLedger** | 持续追加 | 只追加事件流 | 观察者的**信号写入目标** |
| **观察者（新增）** | 节点执行过程中 | 静默文件观察 + 分级信号 | **正交增强层**，不改变图拓扑 |


## 二、观察者设计原则

### 2.1 六条核心原则

**原则 1：只读性（Read-Only Contract）**

观察者严格只读。它监视事件流和文件变化，但不追加事件、不修改产出、不阻塞主流程。参考 multi-agent-lab 的 Observer 设计契约：“观察者永不追加事件。它是严格只读的。世界在有无观察者时运行完全一致”。

**原则 2：非阻塞性（Non-Blocking）**

观察者与工作 Agent 并行运行，不阻塞主流程。Hankweave 的 Sentinel 模型明确：“主 Agent 继续工作，不等待哨兵。如果哨兵出错或耗时过长，主工作流不受影响”。但如果观察者检测到**明确违规**，它可以向编排器发送 RED 信号，由编排器决定是否中断。

**原则 3：文件观察优先（File-Observation First）**

观察者主要通过文件观察（`git diff`、读取变更文件）获取工作产出，而非通过消息传递。PACT 的实证经验：“80% 以上的观察应该是静默文件读取。如果审计者频繁给编码者发消息，说明它在干扰而非观察”。

**原则 4：记忆隔离（Context Isolation）**

观察者不共享工作 Agent 的 context，只读取文件系统和工作产出。这保持了 G4（记忆纯洁性）——观察者的推理过程不污染工作 Agent 的上下文。PACT 明确：“你的上下文与编排器隔离，其他地方加载的技能不会传递给你”。

**原则 5：分级介入（Tiered Intervention）**

观察者根据关注级别采取不同行动，从静默到阻断逐级升级。PACT 的分级模型：“无关注→静默；轻微→内部记录；重要但模糊→发一个具体问题；明确违规→立即发 RED 信号”。

**原则 6：fail-open（故障开放）**

观察者自身故障不应阻塞主流程。Hermes Observer Hooks 的设计：“Hook 回调是 fail-open 的。Hermes 捕获回调异常，记录警告，保持 Agent 循环运行”。


## 三、观察者分层架构

在 L0-L5 分层基础上，观察者作为**横切关注点**嵌入 L2 和 L5：

```
┌──────────────────────────────────────────────────────────────┐
│  L5 可观测性与治理层                                          │
│  观察者信号 → RunLedger（OTEL 对齐）· 策略合规 · 成本熔断       │
├──────────────────────────────────────────────────────────────┤
│  L4 可视化层                                                  │
│  观察者信号染色 · 关注度热力图 · 审计轨迹可视化                 │
├──────────────────────────────────────────────────────────────┤
│  L3 角色管理层                                                │
│  观察者角色配置（observeNodes / interventionMode / criteria）   │
├──────────────────────────────────────────────────────────────┤
│  L2 编排引擎层（StateGraph）                                   │
│  观察者作为节点装饰器 / 边中间件 / 事件订阅者                   │
├──────────────────────────────────────────────────────────────┤
│  L1 执行与记忆层（subagent）                                   │
│  工作 Agent 正常运行，观察者并行读取其产出                      │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 三层观察者

| 层级 | 模式 | 触发时机 | 介入方式 | Token 开销 | 实现复杂度 |
|---|---|---|---|---|---|
| **L1 轻量检查** | 中间件拦截 | 每个节点执行前后 | 纯函数检查（格式、权限、命名规范），不调用 LLM | 零 | 低 |
| **L2 静默观察** | 并发审计者 | 每个角色节点完成后 | 文件观察（git diff、读取产出），按关注级别决定是否发信号 | 低（仅在发现关注时调用 LLM） | 中 |
| **L3 深度审查** | 流式观察者 | 质量门节点、循环回退前 | 完整 LLM 审查，返回 BLOCK/SANITIZE/FLAG | 高（每次完整审查消耗 Token） | 高 |

**建议实施顺序**：MVP-2 实现 L1（零 Token，最快落地），MVP-3 实现 L2（低 Token，核心价值），MVP-6 实现 L3（高 Token，按需启用）。


## 四、观察者契约设计

### 4.1 观察者配置 Schema（L3 YAML 扩展）

在现有角色 YAML schema 基础上，增加观察者配置：

```yaml
observers:
  - id: quality-observer
    role_ref: "R8-quality"                  # 观察者角色（复用现有 R8）
    observe_nodes: ["R3-develop", "R5-test"] # 观察哪些节点的产出
    observation_mode: file-watch            # file-watch | event-stream | hybrid
    intervention_mode: flag-only            # flag-only | sanitize | block
    criteria:                                # 审计标准（按优先级）
      - architecture-drift                   # 架构漂移
      - cross-agent-consistency              # 跨 Agent 一致性
      - requirement-alignment                # 需求对齐
      - security-sensitive-code              # 安全敏感代码
    exclude_criteria:                        # 不审计的内容
      - code-style                           # 代码风格（属于 L1）
      - test-coverage                        # 测试覆盖率（属于 TEST 阶段）
      - micro-optimization                   # 微优化
    dispatch_conditions:                     # 何时部署观察者
      variety_score_gte: 7                   # 多样性评分 ≥7
      parallel_coders_gte: 3                 # 3+ 并行开发
      security_sensitive: true               # 安全敏感代码
      prior_drift_history: true              # 有架构漂移历史
    token_budget: 10000                      # 观察者专属 Token 预算
    max_observations_per_node: 5             # 单节点最大观察次数
```

**关键设计决策**：

- `observe_nodes` 声明观察范围，不改变图拓扑。观察者是**订阅者**，不是图节点。
- `intervention_mode` 默认 `flag-only`，安全场景才允许 `block`。
- `criteria` 按优先级排序，PACT 的审计标准优先级为“架构漂移 > 风险比例关注 > 跨 Agent 一致性 > 横切关注点 > 需求对齐”。
- `dispatch_conditions` 控制观察者的部署时机，避免低复杂度任务被过度观察。PACT 的调度条件：“多样性评分 ≥7、3+ 并行开发、安全敏感代码、有架构漂移历史”。

### 4.2 观察者事件与信号契约

```typescript
// 观察者事件
interface ObserverEvent {
  id: string;
  observer_id: string;            // 观察者 ID
  correlation_id: string;         // 关联的工作流运行 ID
  observed_node: string;          // 被观察的节点 ID
  observed_agent: string;         // 被观察的角色 ID
  timestamp: number;
  observation_type: "file-read" | "diff-check" | "tasklist-check";
  payload: {
    changed_files: string[];      // 变更文件列表
    diff_summary?: string;        // diff 摘要
    artifact_refs?: string[];     // 产出物引用（art://）
  };
}

// 观察者信号
interface ObserverSignal {
  id: string;
  observer_id: string;
  correlation_id: string;
  observed_node: string;
  signal_level: "green" | "yellow" | "red";
  concern_level: "none" | "minor" | "significant" | "critical";
  action: "silent" | "internal-log" | "send-question" | "send-red-signal";
  criteria_matched: string[];     // 命中的审计标准
  evidence_refs: string[];        // 证据引用（文件路径 + 行号）
  summary: string;                // 200 字以内摘要
  timestamp: number;
  token_used: number;             // 本次观察消耗的 Token
}
```

### 4.3 观察者与 StateGraph 的集成方式

**方式 A：节点装饰器（推荐）**

观察者作为节点执行后的可选钩子，不改变图拓扑：

```json
{
  "nodes": [
    { "id": "R3-develop", "roleRef": "R3", "nodeType": "role" }
  ],
  "edges": [
    { "from": "R3-develop", "to": "R5-test", "type": "seq" }
  ],
  "observers": [
    {
      "id": "quality-observer",
      "roleRef": "R8-quality",
      "observeNodes": ["R3-develop", "R5-test"],
      "observationMode": "file-watch",
      "interventionMode": "flag-only",
      "criteria": ["architecture-drift", "requirement-alignment"]
    }
  ]
}
```

**执行流程**：

```
R3-develop 节点开始执行
    ↓
观察者启动（并行）
    ├── Phase A 预热：读取架构文档、计划、dispatch 上下文
    ├── Phase B 观察循环：git diff → 对比参考链 → 分级响应
    └── Phase C 最终观察：扫描所有修改文件 → 发 GREEN/YELLOW/RED 摘要
    ↓
R3-develop 节点执行完成
    ↓
观察者信号写入 RunLedger
    ↓
条件边根据信号决定路由：
    ├── GREEN → 正常进入 R5-test
    ├── YELLOW → 记录到 RunLedger，继续但标记
    └── RED → 触发回退到 R3-develop（或上游节点）
```

**方式 B：事件订阅者（用于 L4 可视化）**

观察者订阅 RunLedger 的事件流，只读消费：

```python
class Observer:
    """Read-only subscriber over the event ledger."""
    def __init__(self):
        self._view = StageProjection()
        self._callbacks = []
    
    def on_change(self, callback):
        """Register a callback invoked whenever the view changes."""
        self._callbacks.append(callback)
    
    def consume(self, event):
        """Apply one event and return the diff."""
        # 观察者不追加事件，只读取和投影
        ...
```

参考 multi-agent-lab 的 Observer 实现：观察者维护自己的 view-state 作为投影，当视图变化时通知注册的回调，多个观察者可以订阅同一个 ledger。


## 五、观察者与现有机制的集成点

### 5.1 对 G2（循环编排）的影响

观察者作为循环回退的**早期触发源**：

| 信号 | StateGraph 路由 |
|---|---|
| GREEN | 继续正常流程 |
| YELLOW | 记录到 RunLedger，继续但标记 |
| RED | 触发回退到上游节点（而非等待质量审核节点） |

这比当前设计的“质量审核节点输出 retry”更早发现问题——在开发过程中就检测到偏离，而非等到开发完成后再回退。

### 5.2 对 L5（可观测性与治理）的补充

观察者信号写入 RunLedger，格式对齐 OpenTelemetry GenAI 语义约定：

- `gen_ai.agent.name` = 观察者 ID（如 `quality-observer`）
- `gen_ai.agent.operation` = `"observe"` | `"flag"` | `"block"`
- 观察结果作为 span event
- 观察者 Token 消耗作为 span attribute：`gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`

### 5.3 对 Token 预算的影响

三层观察者的 Token 开销可控：

| 层级 | Token 开销 | 控制策略 |
|---|---|---|
| L1 轻量检查 | 零 | 纯函数，不调用 LLM |
| L2 静默观察 | 低 | 仅在发现关注时调用 LLM；80%+ 观察为静默文件读取 |
| L3 深度审查 | 高 | 按 `dispatch_conditions` 分级触发；低复杂度任务跳过 |

**建议**：在 L3 角色 YAML 中增加 `token_budget` 字段，观察者超出预算时降级为 L1 模式。


## 六、观察者的落地路径

### 6.1 MVP 集成建议

| MVP | 观察者层 | 集成内容 | 验收标准 |
|---|---|---|---|
| MVP-2 | L1 轻量检查 | 在 StateGraph 节点预处理中增加纯函数检查（格式、权限、命名规范） | 零 Token，检查不通过时返回 `WARN`/`BLOCK` |
| MVP-3 | L2 静默观察 | 实现观察者作为节点装饰器；文件观察 + 分级信号；信号写入 RunLedger | 观察者能检测到架构漂移并发出 YELLOW/RED 信号 |
| MVP-4 | 观察者信号可视化 | 观察者信号在画布上染色；关注度热力图 | 观察者信号实时可见 |
| MVP-5 | 观察者配置导入 | YAML 中的观察者配置解析；用户可在画布上添加观察者 | 零代码配置观察者 |
| MVP-6 | L3 深度审查 | 流式观察者；完整 LLM 审查 | 按需启用，Token 预算可控 |

### 6.2 MVP-3 的具体实现任务

1. **观察者基类**：实现只读 Observer，支持事件订阅和视图投影
2. **文件观察器**：基于 `git diff` 和文件读取的变更检测
3. **信号发射器**：GREEN/YELLOW/RED 信号生成和写入 RunLedger
4. **参考链对比**：架构文档 > 批准的计划 > dispatch 上下文
5. **分级响应逻辑**：根据 `concern_level` 决定 `action`
6. **与 StateGraph 集成**：观察者作为节点装饰器，信号影响条件边路由


## 七、关键决策与风险

### 7.1 待决策

| 决策点 | 选项 | 建议 |
|---|---|---|
| **观察者的介入粒度** | 流式（每 chunk）vs 节点级（每节点完成后）vs 阶段级 | 节点级为主，流式仅用于安全护栏 |
| **观察者的介入权限** | flag-only / sanitize / block | 默认 flag-only，安全场景允许 block |
| **观察者的触发条件** | 无条件 vs 按多样性评分/复杂度 | 按复杂度分级触发，低复杂度跳过 |
| **观察结果的状态表达** | 写入 RunLedger vs 写入 State | RunLedger（历史轨迹），State 只存当前观察信号 |
| **观察者与循环回退的关系** | 观察者触发回退 vs 质量审核节点触发回退 | 观察者触发早期回退（RED），质量审核节点触发终审回退 |
| **观察者是否消耗角色 Token 预算** | 独立预算 vs 共享预算 | 独立预算（`token_budget` 字段），避免观察者挤占工作 Agent 预算 |

### 7.2 风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| **观察者干扰工作 Agent** | 频繁发消息或阻塞执行 | 80%+ 观察为静默文件读取；fail-open；观察者故障不阻塞主流程 |
| **观察者 Token 失控** | 每次观察都调用 LLM | 分级触发（`dispatch_conditions`）；观察者独立 Token 预算；超预算降级为 L1 |
| **观察者与质量审核重复** | 两者都做质量检查 | 明确边界：观察者做过程监控（早期预警），质量审核做终审（节点完成后） |
| **观察者共享 context 污染** | 观察者读取工作 Agent 的推理过程 | 观察者只读取文件系统和工作产出，不读取工作 Agent 的 context |
| **观察者信号延迟** | 观察者信号到达时节点已执行完成 | 节点级观察粒度，信号在节点完成后立即写入 RunLedger，条件边在下一次路由时消费 |

## 九、总结

**观察者机制是当前设计的正交增强，不是替代。**

- 它补的是“在节点执行过程中发现偏离”这一能力，而非替代“节点完成后的质量门”。
- 观察者通过**文件观察**获取工作产出，不共享工作 Agent 的 context，保持了 G4（记忆纯洁性）。
- 观察者默认**静默**，80%+ 的观察是静默文件读取，只有在发现明确违规时才发信号。
- 观察者的介入是**分级**的：GREEN → 继续；YELLOW → 记录；RED → 触发早期回退。
- 观察者的 Token 开销**可控**：L1 零 Token，L2 低 Token（仅在发现关注时调用 LLM），L3 高 Token（按需启用）。

**实施建议**：MVP-2 实现 L1 轻量检查（零 Token），MVP-3 实现 L2 静默观察（核心价值），MVP-4 的看板中展示观察者信号，L3 深度审查推迟到 MVP-6。
