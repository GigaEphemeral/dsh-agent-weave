## 二、整体架构与开发约束

### 2.1 插件双半端契约

本插件以 **Cordis 插件包**形态存在，一个 npm 包同时扮演两个角色：

| 半端 | 运行位置 | 入口文件 | 构建方式 | 职责 |
|---|---|---|---|---|
| **Host 半** | Node 进程 | `lib/index.js`（源码 `src/index.ts`） | tsc 编译（strict + NodeNext ESM） | 注册工具、服务、HTTP 路由、会话事件、子代理调度 |
| **Client 半** | 浏览器 | `lib/client.js`（源码 `src/client/index.tsx`） | tsdown + lightningcss 打包 | 渲染画布、看板、审批面板、观察者信号 |

**package.json 双声明**：

```json
{
  "name": "dsh-agent-weave",
  "dsh": {
    "bundle": "./lib/index.js",
    "client": "./lib/client.js"
  }
}
```

**关键约束**：
- Client 半入口必须是 `.tsx` 文件，否则无法写 JSX
- 相对导入必须带 `.js` 后缀（ESM 要求）
- 类型与运行时必须使用 scoped Cordis（`@deepseek-ai/cordis`），不能保留 unscoped `cordis` import，否则双 Cordis 会导致类型与运行时身份分裂
- `package.json` 依赖中必须使用 `@deepseek-ai/cordis` 作为 peerDependency

### 2.2 Cordis 生命周期契约（硬性）

Cordis 为每个已加载插件实例维护一个 fiber，状态机为 `PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED`。插件可能因配置修改、热重载、显式 `dispose()` 或依赖服务消失而被卸载，清理是自动的。

**对于 Cordis 尚未管理的资源，必须包装在 `ctx.effect()` 中并返回 disposer**。

**本项目的精确约束**：

| 资源类型 | 约束 | 示例 |
|---|---|---|
| **定时器** | 禁止裸 `setTimeout` / `setInterval`；必须 `ctx.effect(() => { const t = setTimeout(...); return () => clearTimeout(t); })` | 循环超时定时器、deadline 检测定时器 |
| **文件句柄** | 禁止裸 `fs.open` / `fs.createWriteStream`；必须 `ctx.effect()` 注册并返回关闭函数 | 日志文件句柄、artifact 存储句柄 |
| **数据库连接** | 禁止裸 `new Database()`；必须 `ctx.effect()` 注册并返回关闭函数 | 若使用 SQLite 作为 checkpoint 存储 |
| **watcher** | 必须 `ctx.effect()` 注册并返回 dispose 函数 | 文件观察器的 `fs.watch` |
| **RunLedger 存储** | **直接使用 `ctx.storageDomain`**（Cordis 一等服务，框架管生命周期），不自行管理 | 审计账本写入 |

**Cordis 注册即 effect**：通过 `ctx` 注册的任何东西（事件监听、工具、定时器）在插件卸载时都会被自动清理。`registerProvider` 本身是 Cordis effect 会自动撤销，但引擎持有的定时器/连接不会。

**热重载测试作为门禁**：每个 MVP 门禁必须包含“插件热重载后无资源泄漏”验证。⚠️ Discussion #2854：HMR recompose 在 fiber disposal 与 recompose 间有竞态，非 effect 资源可能泄漏或过早清理（案例：第三方 bundle 插件 boot 后 ~3s 被静默禁用）。

### 2.3 插件契约约束（不可违反）

每个运行组件必须是可由 DSH 官方 Loader 安装的 out-of-tree Cordis Bundle。**插件不得复制或替代 DSH 的 Agent、Session、Goal、Skill、Tool、Approval、Jobs、Schedule、Workspace、Credential、Storage 或生命周期**。

**这意味着**：
- 不重新实现 Agent 循环（用 `ctx.subagents`）
- 不重新实现 Skill 注册（用 `ctx.skills`）
- 不重新实现 Tool 注册（用 `ctx.tools`）
- 不重新实现 Storage（用 `ctx.storageDomain`）
- 不重新实现生命周期（用 `ctx.effect()`）

**允许的自建范围**：StateGraph 引擎（L2）、角色管理（L3）、可视化（L4）、可观测治理（L5）、生态扩展（L6）。

### 2.4 编码规范约束

| 约束 | 说明 |
|---|---|
| **TypeScript strict** | `tsconfig.json` 开启 strict，不允许 `any`（除非有 `// eslint-disable-next-line` 注释说明） |
| **ESM only** | NodeNext module resolution，相对导入带 `.js` 后缀 |
| **Zod 校验** | 所有外部输入（YAML、图 DSL、消息 payload）必须经 Zod Schema 校验 |
| **日志结构化** | 禁止字符串拼接日志；统一走 `src/shared/logger.ts`，必填 `trace_id` |
| **注释规范** | 对外 API 必须 JSDoc；缺陷规避注释标 `🐛` + Discussion 编号；TODO/FIXME/HACK 必须带责任人或编号 |
| **禁止 console.log** | 统一走 logger |
| **禁止注释掉的代码** | git 有历史 |
| **命令式 + 声明式双路径** | 角色/流程支持 YAML 声明式和画布可视化双路径，二者操作同一底层规范 |

## 四、存储方案

### 4.1 storageDomain 使用规范

DSH 的 `dsh-storage-domain` 是使用存储家族的类型化方式：由所属包声明一次领域——其名称、格式版本与 zod 记录 schema——宿主消费方在已路由后端上打开它，并通过 `ctx.storageDomain` 读写记录。

**关键特性**：
- 每次写入在 resolve 前都已持久，并发出 `domain/changed` 事件，因此读取永远不会与已存介质分叉
- 读取从已验证的内存状态同步返回，写入在 resolve 前持久化并按顺序发出事件
- 产品包绝不直接触碰后端——**它是后端约定的唯一消费方**

**本项目声明的 storage domain**：

```typescript
// src/l5-observability/run-ledger.ts
const runLedgerDomain = ctx.storageDomain.declare({
  name: 'dsh-agent-weave/run-ledger',
  formatVersion: 1,
  schema: z.object({
    graphId: z.string(),
    graphVersion: z.string(),
    node: z.string(),
    state: z.unknown(),
    iteration: z.number(),
    timestamp: z.number(),
  }),
});
```

### 4.2 三域分离

| 域 | Domain 名称 | 格式版本 | 存储内容 | 生命周期 |
|---|---|---|---|---|
| **checkpoint** | `dsh-agent-weave/checkpoint` | 1 | 图执行快照 `{ graphId, graphVersion, node, state, iteration }` | 工作流完成后保留 N 天 |
| **artifact** | `dsh-agent-weave/artifact` | 1 | 交付物文件引用 + 元数据 | 随项目归档 |
| **evolution** | `dsh-agent-weave/evolution` | 1 | genome / 版本 / momentum（Phase 7） | 永久 |

### 4.3 checkpoint 序列化方案

`dsh-state-graph` 的 checkpoint 回调在每次节点补丁合并后调用（载荷 `{ graphId, node, state, iteration }`），适合把状态快照写入 dsh 持久化（session log / `ctx.fs` 由宿主决定）；**回调不应抛错**。

**本项目的序列化契约**：

```
serialise state → durable form（JSON）
    ↓
store.save(session_id, blob)
    ↓
trace.emit("checkpoint.write")
```

**序列化约束**：
- State 中**不得包含不可序列化对象**（函数、Symbol、循环引用、`Date` 对象需转为 ISO 字符串）
- `artifacts` 字段存储 `art://` 引用，不存储内容
- 序列化失败时 **fail-fast**，抛出明确错误而非静默降级

### 4.4 备份与恢复策略

| 场景 | 恢复方式 | 依据 |
|---|---|---|
| 工作流中断 | 从最近 checkpoint 重建 | RunLedger 事件流 |
| 插件热重载 | 无需恢复（内存态重建） | Cordis effect 自动清理 |
| session 膨胀 | `dsh-session-pruner` 自动归档 | one-shot 完成后秒级归档，continuable/main 空闲超 N 天归档 |
| 跨版本升级 | **不依赖 subagent settlement notice 恢复** | 用 RunLedger 重建状态（🐛 Discussion #7065） |
| 图 DSL 变更 | 按 `graphVersion` 判断迁移 | 旧版本继续执行或提示用户迁移 |


## 五、核心 API 契约

### 5.1 StateGraph 引擎 API

参考 `dsh-state-graph` 的核心接口设计：

```typescript
/** 节点处理器：接收 State 和上下文，返回 Partial<State> */
type NodeHandler<T> = (
  state: T,
  ctx: GraphNodeContext,
  signal?: AbortSignal,
) => Promise<Partial<T>>;

/** 条件处理器：返回下一个节点名、并行目标数组、或 "__END__" */
type ConditionHandler<T> = (
  state: T,
  ctx: GraphNodeContext,
) => NodeName | NodeName[] | '__END__';

/** 图执行结果 */
interface GraphExecutionResult<T> {
  graphId: string;
  finalState: T;
  trajectory: TrajectoryEvent[];
  iterations: number;
}

/** StateGraph 实例 */
interface StateGraph<T> {
  addNode(name: string, handler: NodeHandler<T>): void;
  addEdge(from: string, to: string): void;
  addConditionalEdge(from: string, condition: ConditionHandler<T>, maxIter?: number): void;
  addSubagent(name: string, options: SubagentNodeOptions): void;
  addApprovalGate(name: string, prompt: string): void;
  run(initialState: T, options: RunOptions<T>): Promise<GraphExecutionResult<T>>;
}

/** RunOptions 中 checkpoint 是必需参数 */
interface RunOptions<T> {
  checkpoint: (payload: CheckpointPayload<T>) => Promise<void>;
  signal?: AbortSignal;
}
```

### 8.2 数据流总结

```
用户输入一句话需求
    ↓
父代理解析 → 生成 GraphDefinitionSpec（Zod 校验）
    ↓
StateGraph 引擎加载图 → 静态验证器检查
    ↓
节点执行 → 节点返回 Partial<State> → 引擎原子合并
    ↓
checkpoint 回调 → 写入 storageDomain + RunLedger（双写）
    ↓
观察者并行读取文件产出 → 发出 GREEN/YELLOW/RED 信号
    ↓
条件边根据 State + 信号决定路由（继续/回退/审批）
    ↓
工作流完成 → RunLedger 保留完整轨迹
```
