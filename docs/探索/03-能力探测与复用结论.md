## 一、探测口径与已有原生能力

**版本/API 甄别（⚠️，采信实测）：**
- 版本号：外部评审称「DSH 0.1.5-rc2 / agent-team 0.1.5-alpha.2」；实测 checkout 顶层为 `deepseek-ai-dsh-root-0.1.5-rc.1.tgz`、`agent-team/package.json=0.1.5-rc.2`。**不一致**，上线前以实际 `dsh --version` + `npm ls` 为准。
- subagent API 名：外部评审称 `followup()/reportFrom()`；实测服务契约 = `sendMessage(sender, targetId, content)`（无 followup/reportFrom）。跨版本命名差异，采信实测。

源码核查确认，DSH 已有**三个编排底座 + 两个关键横切服务**（📘 全部 `packages/` 下）：

| 类 | 包 | 成熟度 | 一句话 |
|---|---|---|---|
| 执行原语 | `packages/subagent/…` | **核心稳定** | 父子树 + continuable + `SubagentProvider`（角色身份）+ 记忆隔离开关 |
| 团队抽象 | `packages/experimental/agent-team` | **experimental** | lead+teammate + 任务看板(DAG) + 持久邮箱（build on subagents） |
| 编排引擎 | `packages/workflow/…` | **正式 client 目录** | 脚本式编排（agent()/pipeline()/parallel()）+ worker 隔离 + chat 可视化 |
| 目标跟踪 | `dsh-goal`（`ctx.goals`） | **核心稳定** | 会话内保留"当前完成目标"，process-local activation 保持续跑权限 → **MVP-3 任务目标持久化** |
| 后台任务 | `dsh-jobs` / `dsh-jobs-local`（`ctx.jobs`） | **核心稳定** | 九方法 JobRegistry（start/list/kill/wait/onJobDone…）→ **MVP-3 重启恢复** |

> `ctx.goals` + `ctx.jobs` 是官方一等服务：MVP-3 的"重启恢复"直接基于 `ctx.jobs`，角色任务目标追踪基于 `ctx.goals`，不自建。另注意：模型可见的 `ralph` 工具（goal 驱动自动续跑）与 `workflow` 同属编排工具族，MVP-1 临时验证可直接用 `workflow` 工具、不用先写插件。

## 二、DQ-2：编排底座能力差异对比

### 2.1 `subagents`（`ctx.subagents`）— 低层执行原语 📘

- **方法**：`startContinuable`（durable child）、`sendMessage`（定向 sender→targetId）、`interrupt`、`listChildren/listDescendants`、`start`（one-shot）、`registerProvider`、`prompt`(@Remote)。
- **`SubagentProvider`（角色注册表条目）**：
  ```
  name: string
  capabilities: { agentOptions, outputSchema, depthLimit, toolFilter, persona }
  inheritsParentContext: boolean      ← 记忆隔离开关
  agentRouteDefaults?: { provider, model }  ← 角色显式指定模型
  start / prepareContinuable
  ```
- **`SubagentStartRequest` 关键字段**：`persona?: string`（**per-child 角色 persona**，shadow deployment persona）、`toolFilter`（限定角色可见工具）、`agentOptions`（模型/推理/输出 token）、`maxDepth`（委派深度）、`outputSchema`（结构化返回）。
- **记忆隔离**：`prepareContinuable` → `ContinuableCreateSpec.seed?`——有 seed=继承父 log（fork），无 seed=**fresh（全新隔离）**。
- **拓扑**：任意父子树（child→grandchild 所有权链）；**跨进程**：六个 provider（in-process / ACP / Codex / Claude Code / DSH SDK）。
- ⚠️ **无并发上限**：dsh-subagent 无任何数量/并发上限，`maxDepth` 只限深度（默认 3）挡不住广度爆炸（1→N→N²，Discussion #131 实测 ~56 子代理拖死 web UI）——需在引擎/Provider 层自建全局计数。
- ⚠️ **模型继承缺陷（🐛 已确认，影响所有 provider）**：`Agent.options`（provider/model）在 session 创建时冻结，运行中 web model picker 的切换**不传播**到子代理——子代理继承"创建时默认路由"而非父代理当前模型，且错误被吞；spawn 子代理还可能被路由到 `deepseek-official`（计费记错账户）。**结论：角色 YAML 的 `model` 字段必须在创建子代理时显式指定（走 `agentRouteDefaults`/`agentOptions`），不依赖继承。**

### 2.2 `agentTeams`（`ctx.agentTeams`）— 团队抽象层（experimental）📘

- **角色模型**：`lead` + `teammate`（**星型**，单根）；**并发上限 `maxMembers=8`**。
- **spawnTeammate**：`name + description + prompt + context:'fresh'|'fork' + provider`。
- **任务看板（task DAG）**：`TeamTaskView { status, blockedBy[]（依赖）, writeScopes[], ownerName, ready, revision(CAS) }`；`updateTask` action = claim/release/edit/set_dependencies/complete/reopen/reassign/delete。
- **消息**：`sendMessage` → durable mailbox（queued→delivered 事件 + 去重）；**同步**：`waitForChange`；**中断**：`interrupt`（需 lead 权限）。
- **持久化**：全部状态存 **Lead Session log**；**UI**：`experimental/client-ui-agent-team`。
- ⚠️ **实测不兼容证据（📊 PR #257）**：published DSH 0.1.5-rc.2 + Agent Teams 0.1.5-alpha.2 **在 fork 和 spawn 两种模式下均失败**（应对方式 = 创建子代理前暂停不兼容的 Team composition）。**结论：不可作 MVP-3 核心依赖，"task DAG + mailbox"改自建（subagents + storageDomain 足够）。**

### 2.3 `workflowEngine`（`ctx.workflowEngine`）— 脚本编排引擎 📘

- **契约**：`start(WorkflowStartRequest{ script, meta, args?, subagentProvider?, maxTotalAgents?, parent, signal? }) → WorkflowRun{ id, meta, result:Promise, cancel(), dispose() }`。
- **脚本钩子**：`agent(prompt, opts?)`、`pipeline(items, ...stages)`、`parallel(thunks)`、`phase(title)`、`log()`（顶部 await；JSON 返回）。
- **实现**：worker thread 隔离；**落地工具**：`tool-workflow`（=`workflow`）、`tool-ralph`（=`ralph`）——本会话可直接调用，即为铁证。
- **可视化**：`client/ui-workflow-run`——把 run/agent-start/agent-end 事件折叠成 chat 节点，渲染 `{ phases, members[], status }`。
- ⚠️ **引擎级失控闸门**：`maxTotalAgents=1000`（默认，**只能降低不能提高**）、`maxConcurrentAgents`（0=按 CPU 解析）、`syncTimeoutMs`。若图 DSL 编译为 workflowEngine 脚本作过渡，循环回退的失控保护依赖引擎 `maxTotalAgents`，而非脚本内 `retry_count`——这也是不能长期迁就脚本式的论据之一。

### 2.4 对比矩阵

| 维度 | subagents | agentTeams | workflowEngine |
|---|---|---|---|
| 层级 | 低层原语 | 团队抽象 | 编排引擎 |
| 成熟度 | ✅ 核心稳定 | ⚠️ experimental（📊 实测不兼容） | ✅ client 正式 |
| 角色身份 | provider + persona + toolFilter | 复用 provider | subagentProvider?（整链共用） |
| 记忆隔离 | inheritsParentContext / seed | context:'fresh'\|'fork' | 经 agent() 走 subagents |
| 拓扑 | 任意父子树 | 固定星型（maxMembers=8） | 脚本任意（无图） |
| 任务看板 | 无（自管） | task DAG + mailbox | 无 |
| 消息 | sendMessage（定向） | durable mailbox | 无（靠 agent 结果） |
| 循环/条件 | 靠上层逻辑 | 靠 task DAG 迭代 | 靠脚本控制流 |
| 跨进程执行 | ✅ 6 provider | 仅 in-process | ✅ worker thread |
| 取消/中断 | interrupt（需权限） | interrupt（需 lead 权限） | cancel()/dispose() |
| 失控闸门 | depthLimit | maxMembers + maxTasks | maxTotalAgents=1000 |
| 可视化 | 无内置 | TeamView(实验 UI) | chat 节点(ui-workflow-run) |
| Windows | ✅ subagent 可用（Bash 禁用） | ⚠️ 同左 | ⚠️ worker 可用，脚本 bash() 不可用 |

## 三、推荐底座组合 + 已知缺陷 + 待决策

### 3.1 推荐底座（DQ-2 结论：分层复用）

- **执行器（角色身份 + 记忆隔离 + 工具限定）** → `subagents` 的 `SubagentProvider` + `persona` + `toolFilter` + `inheritsParentContext=false`。官方一等接口。
- **任务看板 + 消息邮箱** → **自建**（subagents + storageDomain）：`agentTeams` 有实测不兼容证据（§2.2），不复用。
- **后台任务基座** → **复用 `ctx.jobs`**（九方法契约已覆盖 start/list/kill/wait，自建是重复造轮子）。
- **任务目标持久化** → **复用 `ctx.goals`**（官方一等服务，与 session 生命周期绑定）。
- **MVP-1 编排起步** → `workflowEngine`（脚本式 + worker 隔离 + chat 可视化），写死脚本验证多角色闭环，不建图。

### 3.2 三条红线（不要做清单，已升级）

1. **不直接依赖 experimental `agent-team`**（不支持循环 + API 不稳 + **📊 实测 fork/spawn 均失败**）——task DAG + mailbox 自建。
2. **不用社区团队插件**（版本检测不匹配）。
3. **不自研记忆隔离**（subagent 已提供）。

> 综合：编排引擎主方向 = **自研 StateGraph**（非 workflowEngine script，一致性见 `docs/04`）。

### 3.3 运行时已知缺陷（设计必须规避）

| 缺陷 | 影响 | 规避 |
|---|---|---|
| 子代理继承过期 base 模型（🐛 #4311） | 运行中切模型不传播到子代理，角色跑在预期外模型、错误被吞 | 角色 YAML `model` 创建时**显式指定**（agentRouteDefaults/agentOptions） |
| spawn 子代理路由到 deepseek-official（🐛 #4473） | 计费记错账户 | 同上，显式指定 provider |
| 工具通道无法携带 `settings`（结构性） | `permissionMode` 受控的程序化 dispatch **不存在** | **权限在 provider 层预配置**（toolFilter 声明，R3 shell / R5 只读等） |
| Messages 协议历史 notice 毒化（🐛 #7065） | 跨 0.1.6-alpha.1 升级后旧会话永久不可用（旧 settlement notice 含 reasoning/tool-call blocks，Messages 协议无法表示） | **不依赖 settlement notice 恢复**，用 RunLedger 重建；升级前归档/迁移 |

### 3.4 新增待决策

| 决策点 | 建议 | 理由 |
|---|---|---|
| 后台任务基座 | ✅ 复用 `ctx.jobs` | 九方法契约已覆盖，自建重复造轮子 |
| 目标持久化 | ✅ 复用 `ctx.goals` | 官方一等服务，与 session 绑定 |
| 子代理模型指定 | ✅ **显式指定**（角色 YAML `model`） | 继承有已知缺陷 |
| 权限控制通道 | ✅ **provider 层预配置**（toolFilter） | 官方 dispatch 结构性无法携带 settings |

## 五、可行性结论（任务3）：subagent 隔离 + 预设/skill 区分角色，现实吗？能拓展吗？

**结论：现实，且是官方设计意图（📘 源码为证），但有三处已知缺陷需在设计规避（见 §3.3）。**

1. **角色身份**：`SubagentProvider.name` 即角色；`persona?: string` + `persona` capability = 官方"为每个 subagent 注入角色 persona"接口；persona shadow deployment persona（子代理独有）。
2. **记忆隔离（防污染）**：`inheritsParentContext` + `seed` 是官方一等开关——fresh = 不继承父上下文 = 记忆纯洁；`toolFilter` 进一步限定角色只见自己工具。
3. **拓展性（"每个人都有自己的工作流"）**：
   - **角色可增**：`registerProvider` 是注册表 → "导入文件创建角色" = 注册新 provider（或复用 fork provider + 不同 persona/toolFilter）。✅
   - **工作流可换**：编排逻辑是数据（图 DSL）+ 运行时（自建 StateGraph），与角色解耦 → 一人多工作流、多人多工作流，换图 DSL + 角色集即可。✅
   - **角色资产已就绪**：R1-R10 skill + 阶段二 10 角色 persona，就是"角色内容层"，直接映射 provider/persona。✅
4. **三处规避项**：①模型必须显式指定（继承有缺陷）②权限走 provider 层 toolFilter（settings 不可 dispatch）③task DAG/mailbox 自建（agentTeams 实测不兼容）。

**需求 ↔ 官方能力覆盖映射：**

| 需求 | 覆盖度 | 说明 |
|---|---|---|
| 9/10 角色全流程 | ✅ | 每角色一 `startContinuable` child |
| 一句话自动开始 | ✅ | 父代理接收即建工作流 |
| 循环工作流 | ❌ **缺失** | subagent 无内置循环/条件路由 → 自研 StateGraph(L2) |
| 记忆隔离 | ✅ | 独立 Session + inheritsParentContext=false |
| Agent 间对话 | ⚠️ 部分 | sendMessage 传递，自由对话需自建路由（消息总线） |
| 激活状态可视化 | ❌ 缺失 | 自研 L4 |
| 角色动态导入 | ❌ 缺失 | 自研 L3 + YAML 加载器 |
| 画图连接角色 | ❌ 缺失 | 自研 L4 画布 |
| Token 监控 | ⚠️ 社区有 | dsh-token-stats 或官方 tokenMeter |
| 重启恢复 | ✅ | ctx.jobs 九方法契约直用 |
| 任务目标持久化 | ✅ | ctx.goals 直用 |
