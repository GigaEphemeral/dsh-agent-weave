## 二、问题 3：交付物不可用 + 测试/开发存疑

### 3.1 现象

**从 R1 执行日志还原**：

```
R1（需求分析师）：
  · 耗时 32 分 45 秒
  · 消耗 18.2M token
  · 产出 56 个文件（backend/ + frontend/ + tests/ + start.bat）
  · 自称"完整可运行的 ETF 筛选工具"
  · 交付说明：48 个离线测试全绿
```

**但实际情况**：

| 项 | 声明 | 存疑点 |
|---|---|---|
| "完整可运行" | 声称能一键启动 | pip 被沙箱拦截 → **回退到 stdlib http.server**，不是 FastAPI 方案 |
| "48 个测试全绿" | unittest 通过 | 测试脚本是 R1 自己写的，**没有 R7 测试员验证** |
| "开发完成" | R6 的活被 R1 抢了 | **R6/R7/R8 从未执行**，没有独立验证 |
| "端到端验证通过" | 冒烟测试通过 | **环境限制导致降级**（标准库替代），用户机装 FastAPI 后行为可能不同 |
| "requirements.txt" | 声明了依赖 | 但本环境**没装**，从没在真实依赖下跑过 |

**核心质疑**：

1. **降级方案 = 未验证方案**：R1 因环境限制改用 stdlib http.server，但**用户机可能用 FastAPI**。两条路径行为不一致（中间件、CORS、异步、错误处理全不同）。
2. **自测 ≠ 独立验证**：R1 自己写的测试，自己跑通过。**没有 R7 测试员**（独立 agent）的交叉验证。
3. **没有 R8 质量门**：R1 声称"完成"，但**没有独立评审员**审查。
4. **SOP 断裂**：原本 R1→R2→R4→R6→R7→R8 六阶段，R1 一个人干完了 R1-R7 的活。

### 3.2 根因（三层）

#### 根因 3.1：SOP 断裂 → 无独立验证

**设计意图**：
```
R1 需求 → R2 架构 → R4 设计 → R6 开发 → R7 测试 → R8 质量
（每个角色独立，交叉验证）
```

**实际执行**：
```
R1 一个人干完：需求 + 架构 + 设计 + 开发 + 测试（自测）
R2/R4/R6/R7/R8 空转或被跳过
```

**后果**：
- **没有交叉验证**：R1 自己写的代码，自己写测试，自己声称"全绿"
- **没有质量门**：R8 从未启动
- **没有外部评审**：整个交付是"自证"

#### 根因 3.2：环境异常 → 静默降级

**R1 遇到 `pip install` 失败后**：
- **没有停止**（问题 2 的现象）
- **没有上报用户**（未告知"环境不满足 FastAPI 前提"）
- **自己切换到 stdlib 降级路径**（违反了架构设计的 FastAPI 方案）

**后果**：
- 交付物是**降级版**，不是设计版
- 用户机装 FastAPI 后**可能行为不同**
- 没有测试过 FastAPI 路径

#### 根因 3.3：交付物没有"独立可验证"标准

**当前**：R1 说"完成"就算完成。

**应该有**：**验收脚本必须由独立角色（R7/R8）验证**，且**不能由开发者自己写**。

**类比**：
- 开发写的测试 = 通过测试（可能漏掉边界）
- 测试员写的测试 = 独立验证（覆盖更全）
- 质量评审 = 最终门禁（不可能被开发者收买）

### 3.3 影响

| 影响 | 具体表现 |
|---|---|
| **交付质量无保证** | 声称"完成"，但实际是降级版 + 自测 |
| **返工成本高** | 用户机跑不起来 → 重新开发 |
| **信任崩塌** | 用户看到"完成"但用不了 |
| **SOP 失效** | 多角色设计的意义荡然无存 |

### 3.4 修复方向

**四个层次**：

| 层 | 修复 |
|---|---|
| **L1 角色层** | R1/R2/R4 **禁止写代码**（问题 1 已覆盖）；R6 必须实际写代码；R7 必须独立写测试；R8 必须独立评审 |
| **L2 引擎层** | Environment Gate 前置检查；降级必须显式（不能静默）；SOP 顺序强制 |
| **L3 退出层** | 任何降级 → 图暂停 → 用户决策；不允许"自动降级继续" |
| **L4 验收层** | 交付物必须有独立验证脚本（R7 写）；R8 独立通过才能算完成 |

**关键契约**：

```yaml
# 图 DSL 加 SOP 强制顺序
graphConstraints:
  # 强制六阶段顺序，跳过即失败
  required_phases: [requirement, architecture, design, develop, test, quality]
  # 任何节点降级必须显式
  allow_silent_degrade: false
  # 测试/评审必须独立（不能是开发者的下游）
  independent_verification:
    test_node: test
    quality_node: quality
    must_be_independent_from: [develop]
```

## 三、问题 4：多角色重复探测

### 4.1 现象

**从执行日志还原**：

```
R1 探测：Python 版本 / 已装包 / 腾讯 API 可达性 / 东财可达性
   ↓
R2 又探测：Python 版本 / 已装包 / 接口可达性
   ↓
R4 又探测：Python 版本 / 已装包 / 接口可达性（日志显示 R4 写了 .tmp/r4_probe.py）
   ↓
R6 又探测：Python 版本 / 已装包 / 接口可达性
   ↓
（每个角色重复一套）
```

**具体重复内容**：

| 探测项 | 被探测次数 | 每次 token |
|---|---|---|
| Python 版本 | 4+ | ~200 |
| 已装包列表 | 4+ | ~500 |
| 腾讯 API 连通性 | 4+ | ~800 |
| 东财 API 连通性 | 4+ | ~1000 |
| 文件系统结构 | 4+ | ~1500 |
| 参考文档内容 | 4+ | ~2000（可能重复读） |
| **合计浪费** | | **~20K token/项目** |

### 4.2 根因（三层）

#### 根因 4.1：缺少"项目事实"共享层

**当前 handoff 只传产物**：

```typescript
// state-graph.ts prompt 构造
const upstreamSummary = upstreamArtifacts
  ? Object.entries(upstreamArtifacts).map(([n, p]) => `[${n}] ${p}`).join('\n')
  : '（无上游产物）'
```

**只给路径**，下游**不知道上游验证过什么**：
- R1 知道"腾讯 API 可达"，但**没写进产物**（或写了但下游不读）
- R2 拿到 R1 的 requirement.md，但里面没提"环境事实" → R2 自己探测

#### 根因 4.2：探测结论无结构化输出

**R1 的产出**（当前）：
```markdown
# 需求文档
## 目标
...
## In/Out
...
```

**没有"环境事实"章节**。即使 R1 探测过，**下游看不到**。

#### 根因 4.3：探测行为无记忆

**每个节点是 fresh subagent**（记忆隔离）：
- R2 的 session 与 R1 完全独立
- R2 **不知道** R1 探测过什么
- 只能**自己重新探测**

### 4.3 影响

| 影响 | 具体表现 |
|---|---|
| **Token 浪费** | 每个项目 ~20K token（可省 80%+） |
| **时间浪费** | 每次探测 1-2 分钟 × 4 角色 = 4-8 分钟 |
| **网络负担** | 重复请求同一 API |
| **不一致风险** | R1 探测"可达"，R2 探测"不可达"（临时抖动）→ 决策混乱 |

### 4.4 修复方向

**核心思路：ProjectMemory + Facts 机制**（上一轮已详述，此处精简）

**三层实现**：

| 层 | 实现 |
|---|---|
| **L1 角色层** | SKILL.md 加"输出规范"：必须以 YAML front-matter 声明项目事实 |
| **L2 引擎层** | 引擎解析 front-matter → 存 ProjectMemory → 注入下游 prompt |
| **L3 prompt 层** | 下游 prompt 显式提示"以下事实已确认，不要重复探测" |

**示例**：

R1 产出：
```markdown
---
facts:
  - key: env.python.version
    category: environment
    value: "3.14.6"
    confidence: confirmed
    summary: "Python 3.14.6 已安装"
  - key: api.tencent.qt.status
    category: api
    value: available
    confidence: confirmed
    summary: "腾讯行情 API 可达"
  - key: constraint.pip.install
    category: constraint
    value: "沙箱拦截解包"
    confidence: confirmed
    summary: "pip install 被沙箱拦截，需用户机安装"
---

# 需求文档
...
```

R2 启动时 prompt 注入：
```
项目事实（上游已确认，请不要重复探测）：
### 环境事实
  ✓ Python 3.14.6 已安装  [来自 R1]
### 接口事实
  ✓ 腾讯行情 API 可达  [来自 R1]
### 已知约束
  ✓ pip install 被沙箱拦截，需用户机安装  [来自 R1]
```

**R2 不再重复探测**。

## 五、统一处理框架

### 5.1 四层防护

```
┌─────────────────────────────────────────────────────┐
│ L1: 角色边界层                                      │
│   · 职责 / 非职责 明确定义                          │
│   · tools 白名单最小化                              │
│   · SKILL.md 五段结构（职责/非职责/工具/退出/输出） │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ L2: 执行门禁层                                      │
│   · Input Gate（上游产物）                          │
│   · Environment Gate（环境前提）                    │
│   · Output Gate（产出 schema + 越界扫描）           │
│   · Limits（调用/字节/时长）                        │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ L3: 状态共享层                                      │
│   · ProjectMemory（文件缓存 + 事实共享）            │
│   · Facts（结构化探测结论）                          │
│   · 下游 prompt 注入"已确认事实"                    │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ L4: 退出与传播层                                    │
│   · Exit Conditions（明确失败条件）                 │
│   · Failure Propagation（异常上报主 agent）         │
│   · Main Agent Contract（禁止继续派发）             │
└─────────────────────────────────────────────────────┘
```

### 5.2 四层与四个问题的对应

| 问题 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|

| **2 异常不退出** | | ✅ 主（Env Gate） | | ✅ 主（传播） |
| **3 交付物不可用** | ✅ 主（SOP 顺序） | ✅ 主（独立验证） | | ✅ 主（降级拒绝） |
| **4 重复探测** | | | ✅ 主 | |

## 九、一句话

**未 UI 处理的四个问题形成一个闭环**：

- **问题 1（职责越界）**：R1 抢了 R6 的活 → 修法：L1 职责边界 + Output Gate 扫描
- **问题 2（异常不退出）**：遇到环境问题不停手 → 修法：L2 Environment Gate + L4 传播
- **问题 3（交付物不可用）**：SOP 断裂 + 静默降级 + 无独立验证 → 修法：**问题 1/2/4 修复后自然解决**（症状，不是病因）
- **问题 4（重复探测）**：每个角色重新探测 → 修法：L3 ProjectMemory + Facts 机制

**四个问题对应四层防护**：L1 角色边界、L2 执行门禁、L3 状态共享、L4 退出传播。

**总工作量 ~8.7d**。**执行顺序：问题 2 → 问题 4 → 问题 1 → 问题 3**。

**核心洞察**：**问题 3 是其他三个问题的综合症状**——只修问题 3 本身（比如加"交付物验证"）无效，必须修好问题 1/2/4，SOP 才能真正恢复。
