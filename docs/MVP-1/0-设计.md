# MVP-1：单链脚本验证 · 工作梳理与设计

> 版本：v1（2026-09-22）｜依据：`00-开发计划.md` MVP-1 + `04-MVP与设计契约.md`
> 定位：**从"一堆 skill"到"可协作的角色"**——验证角色能否作为 SubagentProvider 被正确编译、注册、执行、隔离
> 范围声明：MVP-1 **不建图、不碰 UI、不实现 checkpoint/消息总线/RunLedger**，这些是 MVP-2/3 的事


## 一、阶段定位与范围

### 1.1 这个阶段到底在验证什么

MVP-1 是一个**验证性阶段**，不是产品化阶段。它要回答四个问题：

| # | 待验证问题 | 为什么重要 | 验证方式 |
|---|---|---|---|
| Q1 | 角色 YAML 能否编译为可注册的 SubagentProvider？ | 这是 L3 角色管理的根基，后续所有角色都走这条路径 | 编译 R6 并注册到 `ctx.subagents` |
| Q2 | 记忆隔离是否真的生效？ | G4（记忆纯洁性）是三条命门之一，如果这里不生效，后续全盘设计失效 | 启动 R3 和 R5，检查 Session 不共享 |
| Q3 | toolFilter 是否真的按角色限定工具？ | 这是最小权限声明的基础，也是 L5 治理的前提 | 检查 R6 的可用工具列表 |
| Q4 | 多角色能否通过 workflowEngine 串行协作？ | 这是"角色协作闭环"的最小验证，MVP-2 的图编排建立在这个基础之上 | 脚本串行 R1→R8，产出完整交付物 |

**关键判断**：MVP-1 用 `workflowEngine` 是**临时的**。workflowEngine 是脚本式的，表达条件边/循环/精确节点状态很别扭——这正是 MVP-2 要换成自研 StateGraph 的原因。MVP-1 用它的唯一理由是：**它现成、能跑、能快速验证角色协作**。

### 1.2 这个阶段明确不做的事

| 不做 | 为什么 | 留到哪个阶段 |
|---|---|---|
| 图 DSL 定义 | 这是 MVP-2 的核心 | MVP-2 |
| StateGraph 引擎 | 这是 MVP-2 的质变点 | MVP-2 |
| checkpoint 契约 | 依赖图 DSL 的状态模型 | MVP-2 |
| 消息总线 | MVP-1 用 workflowEngine 的结果传递，不需要消息总线 | MVP-3 |
| RunLedger | MVP-1 不需要审计账本 | MVP-3 |
| 观察者 | MVP-1 只验证角色协作，不验证质量监控 | MVP-2（L1）起 |
| 画布/看板 | 纯 Host CLI 先行，不碰 UI | MVP-4 |
| Token 熔断 | MVP-1 不做熔断，只做基础验证 | MVP-3 |
| 生命周期管理 | MVP-1 的角色都短生命周期，不需要 resident/on-demand | MVP-3 |

**边界原则**：MVP-1 只做**角色编译 + 单链验证**两件事。任何超出这个范围的实现，都是过度设计。

### 3.2 角色编译流水线（核心）

这是 MVP-1 的核心设计。角色从 YAML 到可执行的 SubagentProvider，经过五个阶段：

```
roles/R6-developer.yaml
    ↓ ① 读取 YAML
    ↓ ② Zod Schema 校验
    ↓ ③ 加载 system_prompt_ref 指向的 skill 文件
    ↓ ④ 映射字段到 SubagentProvider
    ↓ ⑤ 注册到 ctx.subagents
SubagentProvider（可执行）
```

**① 读取 YAML**

从 `roles/` 目录读取角色定义文件。文件内容为 YAML 格式，包含 `id` / `name` / `system_prompt_ref` / `traits` / `tools` / `model` / `memory_scope` / `lifecycle` 等字段。

**② Zod Schema 校验**

用 `RoleDefinitionSchema` 校验 YAML 结构。校验失败的 YAML 不进入编译流程，直接抛出 `RoleLoadError`，错误信息包含字段路径和期望类型。

**③ 加载 system_prompt_ref**

`system_prompt_ref` 指向 `skills/` 目录下的 Markdown 文件。编译器读取该文件内容作为角色的 `persona`。**这是 MVP-1 的关键设计决策**：Prompt 内容来自精心调优的 skill 文件，而不是从 `traits` 自动组装。YAML 只承载结构化元数据。

**④ 映射字段到 SubagentProvider**

| YAML 字段 | SubagentProvider 字段 | 映射规则 |
|---|---|---|
| `id` | `name` | 直接映射 |
| `system_prompt_ref` 文件内容 | `capabilities.persona` | 读取文件内容 |
| `tools` | `capabilities.toolFilter` | 直接映射为数组 |
| `model.provider` + `model.model` | `capabilities.agentOptions` | **必须传完整对象**（🐛 缺陷规避） |
| `memory_scope` | `inheritsParentContext` | `private` → `false`，`shared` → `true` |
| `max_concurrent_children` | `capabilities.depthLimit` | 直接映射 |

**⑤ 注册到 ctx.subagents**

调用 `ctx.subagents.registerProvider(provider)` 注册。注册本身是 Cordis effect，插件卸载时自动撤销。

### 3.3 单链脚本数据流

MVP-1 用 workflowEngine 串行执行六个角色：

```
用户一句话需求
    ↓
workflowEngine.agent(R1, prompt)
    ↓ 产出：PRD
    ↓ 落盘：productions/R1-requirement/prd.md
    ↓
workflowEngine.agent(R2, prompt + upstream)
    ↓ 产出：架构文档
    ↓ 落盘：productions/R2-architect/arch.md
    ↓
workflowEngine.agent(R4, prompt + upstream)
    ↓ 产出：详细设计
    ↓ 落盘：productions/R4-designer/design.md
    ↓
workflowEngine.agent(R6, prompt + upstream)
    ↓ 产出：代码
    ↓ 落盘：productions/R6-developer/src/
    ↓
workflowEngine.agent(R7, prompt + upstream)
    ↓ 产出：测试报告
    ↓ 落盘：productions/R7-tester/report.md
    ↓
workflowEngine.agent(R8, prompt + upstream)
    ↓ 产出：质量审核
    ↓ 落盘：productions/R8-quality/review.md
    ↓
最终产出：完整交付物包
```

**数据流设计要点**：

| 要点 | 设计 | 理由 |
|---|---|---|
| **交付物传递** | 上游产出落盘，下游通过文件路径读取 | 保持记忆隔离，不共享 context |
| **脚本内 prompt 构造** | 下游 prompt 中只携带上游产出**摘要 + 文件路径**，不携带全文 | 控制上下文大小 |
| **产物目录结构** | `productions/<角色ID>/` 独立目录 | 工作区卫生，避免多角色产出混杂 |
| **失败行为** | fail-fast：任一角色失败，脚本停止 | MVP-1 不做恢复，失败即暴露问题 |

### 3.4 关键设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| **Prompt 来源** | `system_prompt_ref` 指向 skill 文件，不从 traits 组装 | traits 是元数据，用于画布显示和边依赖；Prompt 内容需要精心调优 |
| **model 传参方式** | 传完整 `{ provider, model }` 对象，不依赖继承 | 🐛 子代理继承 session 创建时冻结的默认路由，且 spawn 可能路由到 deepseek-official 错账户 |
| **记忆隔离开关** | `memory_scope: private` → `inheritsParentContext: false` | G4 记忆纯洁性的实现基础 |
| **交付物传递** | 文件落盘 + 摘要引用，不传全文 | 控制上下文，为 MVP-2 的 `art://` 引用预演 |
| **Client 半端** | MVP-1 只做空壳，不实现 | 纯 Host CLI 先行，UI 留到 MVP-4 |
| **错误处理** | 编译期 Zod 校验，运行期 fail-fast | MVP-1 是验证阶段，错误要暴露不要掩盖 |


## 四、详细设计

### 4.1 插件入口（src/index.ts）

**Cordis 插件契约**：

```typescript
import type { Context } from '@deepseek-ai/cordis';

export const name = 'dsh-agent-weave';
export const inject = ['subagents', 'skills'];  // 声明依赖的服务

export interface Config {
  /** 角色定义文件所在目录，默认 ./roles */
  rolesDir?: string;
  /** 技能文件所在目录，默认 ./skills */
  skillsDir?: string;
}

export function apply(ctx: Context, config: Config = {}): void {
  // 1. 解析配置
  const rolesDir = config.rolesDir ?? resolveDefaultRolesDir();
  const skillsDir = config.skillsDir ?? resolveDefaultSkillsDir();

  // 2. 加载所有角色 YAML
  const roleFiles = scanYamlFiles(rolesDir);

  // 3. 逐个编译并注册 Provider
  for (const file of roleFiles) {
    const roleDef = loadRoleDefinition(file);
    const provider = compileRoleToProvider(roleDef, { skillsDir });

    // 注册即 effect：插件卸载时自动撤销
    ctx.subagents.registerProvider(provider);

    ctx.logger.info('role-loader', `注册角色 ${roleDef.id}`, {
      role_id: roleDef.id,
      tool_count: roleDef.tools.length,
      memory_scope: roleDef.memory_scope,
    });
  }
}
```

**关键约束**：
- `name` 必须是插件 ID（`dsh-agent-weave`）
- `inject` 声明依赖的服务，Cordis 会在依赖就绪后才调用 `apply`
- 所有注册动作通过 `ctx` 完成，自动纳入生命周期管理
- 不在 `apply` 中执行异步初始化（Cordis 的 apply 是同步的）

### 4.3 角色 Provider 编译器（src/l3-roles/role-loader.ts）

**主函数签名**：

```typescript
/**
 * 将角色 YAML 编译为 SubagentProvider。
 *
 * 🐛 必须显式传入完整 { provider, model } 对象：
 *    DSH Discussion #4311 确认子代理会继承 session 创建时冻结的默认路由，
 *    运行中切换模型不会传播到子代理，且错误被静默吞没。
 *    DSH Discussion #4313 确认 spawn 可能路由到 deepseek-official 错账户。
 *
 * @param role - 通过 Zod Schema 校验的角色定义
 * @param options - 编译选项（skillsDir 等）
 * @returns 可注册到 ctx.subagents 的 Provider
 * @throws {RoleLoadError} skill 文件不存在或读取失败
 */
export function compileRoleToProvider(
  role: RoleDefinition,
  options: { skillsDir: string },
): SubagentProvider;
```

**实现步骤**：

```
① 解析 system_prompt_ref 路径
   → 相对路径基于 skillsDir 解析
   → 绝对路径直接使用

② 读取 skill 文件
   → 不存在则抛 RoleLoadError
   → 读取失败则抛 RoleLoadError（含 errno）

③ 映射字段
   name ← role.id
   persona ← skill 文件内容
   toolFilter ← role.tools
   agentOptions ← { provider: role.model.provider, model: role.model.model }
   depthLimit ← role.max_concurrent_children
   inheritsParentContext ← (role.memory_scope === 'shared')

④ 返回 Provider
```

**错误处理**：

| 错误场景 | 错误类型 | 错误信息 |
|---|---|---|
| skill 文件不存在 | `RoleLoadError` | `skill 文件不存在: <path>（由 <roleId>.system_prompt_ref 引用）` |
| skill 文件读取失败 | `RoleLoadError` | `skill 文件读取失败: <path>: <errno>` |
| YAML 校验失败 | `RoleSchemaError` | Zod 错误路径 + 期望类型 + 实际值 |
| `system_prompt_ref` 路径逃逸 | `RoleLoadError` | `skill 路径不允许逃逸 skillsDir: <path>` |

**关键约束**：
- **路径逃逸防护**：`system_prompt_ref` 解析后的路径必须位于 `skillsDir` 之内，不允许 `../../../etc/passwd` 类型的逃逸
- **不缓存 skill 内容**：每次编译都重新读取，避免热重载后使用过期内容
- **不做 Promise**：编译器是同步函数，异步 IO 由调用方处理（Cordis 的 apply 是同步的）

### 4.4 结构化日志（src/shared/logger.ts）

**核心设计**：

**MVP-1 的日志要求**：
- 角色加载成功/失败记 `info` / `error`
- Provider 注册记 `info`
- 每个角色的 system_prompt 内容**不记录**，只记录长度和 hash
- `trace_id` 在脚本执行时贯穿

### 4.5 单链脚本（workflowEngine）

**脚本结构**：

```typescript
// 伪代码，实际用 DSH workflowEngine 的 agent() 钩子
async function runChain(userInput: string) {
  phase('需求分析');
  const prd = await agent(`你是 R1 需求分析师。用户需求：${userInput}`, {
    provider: 'R1-requirement',
  });
  await writeArtifact('R1-requirement', 'prd.md', prd);

  phase('架构设计');
  const arch = await agent(
    `你是 R2 架构师。基于 PRD 设计架构。PRD 摘要：${truncate(prd, 500)}。完整 PRD 见：art://R1-requirement/prd.md`,
    { provider: 'R2-architect' },
  );
  await writeArtifact('R2-architect', 'arch.md', arch);

  // ... R4 → R6 → R7 → R8 同理
}
```

**关键设计**：
- 每个 `agent()` 调用的是一个**独立的子代理 Session**（`inheritsParentContext=false`）
- 下游 prompt 中只携带上游产出的**摘要 + 文件路径**，不携带全文
- 产物落盘到 `productions/<角色ID>/` 目录
- 任一 `agent()` 抛错则脚本 fail-fast

## 七、与后续 MVP 的衔接

MVP-1 的产出直接喂给 MVP-2：

| MVP-1 产出 | MVP-2 如何使用 |
|---|---|
| `SubagentProvider` 编译逻辑 | MVP-2 的 StateGraph 节点通过 `roleRef` 引用这些 Provider |
| 角色 YAML Schema | MVP-2 的图 DSL 中 `roleRef` 指向已注册的角色 |
| 结构化日志基础设施 | MVP-2 的 RunLedger 事件流复用日志的 `trace_id` 关联 |
| 交付物落盘机制 | MVP-2 的 `art://` 工件引用直接基于 `productions/<角色ID>/` 目录 |

**MVP-1 是 MVP-2 的地基**：地基不牢，MVP-2 的图编排会建立在流沙上。所以 MVP-1 的四项门禁必须全部通过，才能启动 MVP-2。
