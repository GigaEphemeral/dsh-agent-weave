# 软件工程任务拆解方法论

将软件工程的目标转化为**可执行、可验收、可交接**的任务清单。

## 一、核心原则（五条）

| # | 原则 | 含义 |
|---|---|---|
| 1 | **架构先行** | 代码结构从第一天按大目标设计，后续只填充实现，不重构骨架 |
| 2 | **每任务可测** | 每个任务有具体交付物 + 可执行的验证方式，禁止"完成了但没法验证" |
| 3 | **门禁即契约** | Entry/Exit/Stage 三级门禁，未过不启动、不推进、不跳过 |
| 4 | **验收人独立观测** | 验收人不读代码也能验收——必须有可视化或可执行命令 |
| 5 | **预研前置** | 外部依赖和关键技术不确定性，必须在依赖它的任务启动前完成预研 |

## 二、拆解流程（六步）

### Step 0：确认任务类型

先判断属于哪一类，决定后续拆解深度：

| 类型 | 特征 | 拆解深度 |
|---|---|---|
| **Bug 修复** | 单点、明确、短期 | 1-3 个任务，1-3 天 |
| **功能开发** | 有明确需求、影响若干模块 | 5-15 个任务，1-4 周 |
| **系统/项目** | 多模块、多阶段、多角色 | 20-60 个任务，1-6 个月 |
| **重构/迁移** | 保持行为、改变结构 | 10-30 个任务，2-8 周 |
| **探索/预研** | 目标不完全明确 | 按"问题 → 假设 → 验证"拆，产出研究报告 |

**输出**：一句话说明"这是什么类型的任务 + 目标是什么"。

### Step 1：确认需求边界

三件事必须明确，避免方向跑偏：

- **最终目标**：一句话说清"做出来是什么样"
- **明确不做**：列出边界外内容，防止范围蔓延
- **硬性约束**：技术栈、运行环境、合规要求、预算

**输出**：一段"目标 + 边界 + 约束"的声明。

### Step 2：划分阶段（Phase）

按**能力跃迁**划分，而非按时间。每个阶段回答："这个阶段结束后，系统能做什么之前做不到的事？"

**好的阶段划分**：
- 每个阶段是**质变点**（如"从能跑通到能持久"、"从单机到分布式"）
- 阶段之间有明确依赖，不可跳过
- 每个阶段的产出是下一个阶段的输入

**常见阶段模式**：
- **骨架 → 核心 → 完善 → 优化**
- **PoC → MVP → 生产 → 规模化**
- **读 → 写 → 一致性 → 高可用**
- **单点 → 串联 → 并联 → 自愈**

**输出**：阶段总览表（阶段名 / 核心目标 / 周期 / 前置）。

### Step 3：任务拆解（Task）

每个阶段拆成 **5-20 个任务**。粒度标准：

| 维度 | 合格 | 不合格 |
|---|---|---|
| 预估工时 | 0.5d - 3d | > 3d（太大）或 < 0.5d（太碎） |
| 交付物 | 具体文件/类/函数/报告 | "完成 X 功能" |
| 依赖 | 明确列出前置任务 | "无依赖"但不自洽 |
| 验收 | 可执行命令或明确检查项 | "看起来对就行" |

**任务卡片必含五要素**：
1. 任务概要（ID / 名称 / 交付物 / 预估 / 依赖）
2. 开发步骤（给执行者的具体指引）
3. 门禁（Entry Gate / Exit Gate）
4. 验收人检查方法（命令行 + 期望输出）
5. 证据归档（文件位置）

模板见 `references/task-card-template.md`。

### Step 4：门禁设计（Gate）

**三级门禁体系**：

| 类型 | 作用 | 违反后果 |
|---|---|---|
| **Entry Gate** | 任务启动前置条件 | 未满足，任务禁止启动 |
| **Exit Gate** | 任务完成标准 | 未通过，任务视为未完成 |
| **Stage Gate** | 阶段收口 | 未通过，禁止进入下一阶段 |

**门禁设计要点**：
- 每个门禁必须有**可执行命令**或**明确检查项**，禁止写"通过"两字
- Exit Gate 应能拦住不合格产出，而不是走过场
- Stage Gate 应有验收人签署位

模板见 `references/gate-system-template.md`。

### Step 5：验收人观测设计

**核心原则**：验收人不需要读代码，也能通过可执行命令 + 可视化输出完成验收。

**三通道设计**：

| 通道 | 用途 | 落地方式 |
|---|---|---|
| **命令通道** | 快速验证功能正确性 | 单测 + 集成测试 + CLI 命令 |
| **可视化通道** | 运行中实时观测 | 终端实时视图 / HTML 报告 / 图可视化 |
| **文档通道** | 阶段复盘 | 门禁报告 + 验收记录 |

**验收人必备三件套**：
1. **一键验收脚本**：跑完输出"全绿/有失败"
2. **可视化观测**：运行中能看到"现在在做什么、做到哪了、有没有异常"
3. **验收报告模板**：验收人签字确认

模板见 `references/acceptance-observability.md`。

### Step 6：反模式自查

拆解完成后用 `references/anti-patterns.md` 逐项检查。

## 三、软件工程特有的拆解维度

通用任务拆解之外，软件工程还要考虑以下维度：

### 3.1 交付物维度

| 类型 | 交付物 | 特点 |
|---|---|---|
| **代码** | 文件/类/函数/模块 | 有编译、测试、lint 约束 |
| **文档** | 设计文档/接口文档/README | 有格式、完整性要求 |
| **配置** | YAML/JSON/环境变量 | 有 Schema 校验 |
| **数据** | Schema/迁移脚本/种子数据 | 有版本兼容性要求 |
| **测试** | 单测/集成/E2E | 有覆盖率、断言质量要求 |

**拆解时明确每个任务的交付物类型**——不同类型验收方式不同。

### 3.2 质量维度

软件工程的质量不是"能跑"，而是：

| 维度 | 检查方式 |
|---|---|
| **正确性** | 单元测试 + 集成测试 |
| **可维护性** | 代码审查 + lint 规则 |
| **性能** | 基准测试（数字） |
| **安全** | 依赖扫描 + 输入校验 |
| **兼容性** | 跨平台/跨版本测试 |
| **可观测性** | 日志 + 指标 + 追踪 |

**关键点**：每个质量维度必须有**可量化**的标准，否则无法验收。

### 3.3 变更维度

软件工程的本质是**持续变更**，拆解时必须考虑：

| 变更场景 | 拆解策略 |
|---|---|
| **新功能** | 按"接口设计 → 实现 → 测试 → 集成"拆 |
| **重构** | 按"行为固化测试 → 结构变更 → 回归验证"拆 |
| **迁移** | 按"双写 → 灰度 → 切换 → 回滚预案"拆 |
| **依赖升级** | 按"兼容性评估 → 隔离验证 → 灰度 → 全量"拆 |
| **架构演进** | 按"抽象层 → 新旧并存 → 逐步替换 → 清理"拆 |

### 3.4 交接维度

多人协作时，任务之间的交接必须明确：

| 交接类型 | 明确内容 |
|---|---|
| **代码交接** | 接口签名、依赖关系、测试要求 |
| **文档交接** | 格式、必含章节、审核人 |
| **环境交接** | 依赖版本、配置项、启动命令 |
| **数据交接** | Schema、样本、迁移方式 |

### 3.5 风险维度

软件工程的风险分类：

| 风险类型 | 例子 | 缓解 |
|---|---|---|
| **技术风险** | 依赖不兼容、性能不达标 | 预研前置、PoC |
| **需求风险** | 需求模糊、频繁变更 | 明确边界、变更冻结 |
| **协作风险** | 接口不一致、并行冲突 | 契约先行、接口冻结 |
| **交付风险** | 延期、质量不达标 | 门禁强制、可视化监控 |
| **运维风险** | 部署失败、回滚困难 | 蓝绿部署、灰度 |

## 四、不同规模项目的裁剪

### 4.1 Bug 修复（1-3 天）

```
1. 复现（写出失败的测试）
2. 定位（缩小范围）
3. 修复（改代码）
4. 回归（跑全量测试）
5. 提交（附复现步骤）
```

**不需要**：阶段划分、门禁体系、可视化观测。

### 4.2 功能开发（1-4 周）

```
Phase 1：接口设计（1-3 任务）
Phase 2：实现（3-8 任务）
Phase 3：测试（2-4 任务）
Phase 4：集成（1-2 任务）
```

**需要**：Exit Gate（每个任务）、验收观测（关键任务）。

### 4.3 系统/项目（1-6 个月）

完整应用本 skill 的六步流程。

**额外需要**：
- 阶段之间的交接文档
- 角色分工（谁做什么）
- 风险登记表
- 变更管理流程

### 4.4 重构/迁移（2-8 周）

**特殊考虑**：
- 行为固化测试先行（锁住现有行为）
- 新旧并存（不要一次切换）
- 可回滚（每步都能退）

## 五、输出清单

拆解完成后必须产出：

- [ ] 任务类型判断（一句话）
- [ ] 阶段总览表
- [ ] 任务清单（含门禁列）
- [ ] 每个任务的详细卡片（五要素）
- [ ] Stage Gate 检查清单
- [ ] 一键验收脚本
- [ ] 验收报告模板
- [ ] 反模式自查

## 六、拆解时的常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 按时间拆而非按能力拆 | 阶段无质变，进度假象 | 问"这阶段结束后能做什么之前做不到的" |
| 任务太大（> 3d） | 无法独立验收 | 拆成"能独立测试"的最小单元 |
| 任务太碎（< 0.5d） | 管理成本 > 执行成本 | 合并到 1d 左右 |
| 门禁只写"通过" | 无法验证 | 每个门禁必须有可执行命令或明确检查项 |
| 验收人无从下手 | 交付即失联 | 必须有可视化 + 一键脚本 |
| 预研后置 | 开发中途发现依赖不可用 | 预研前置，通过才启动开发 |
| 忽略交接 | 多人协作时接口不一致 | 契约先行，接口冻结 |
| 没有回滚方案 | 出问题无法退 | 每个变更任务必须有回滚步骤 |
| 只测 happy path | 边界/异常未覆盖 | 明确"正常/边界/异常"三类用例 |

## 七、使用方式

用户提出拆解需求时：

1. **Step 0**：先判断任务类型（Bug/功能/系统/重构/预研）
2. **Step 1**：确认目标 + 边界 + 约束
3. **Step 2-4**：按规模裁剪流程，划分阶段 → 拆任务 → 设门禁
4. **Step 5**：设计验收人观测手段
5. **Step 6**：用反模式清单自查
6. **输出**：单一 Markdown 文档，可直接交给执行者（人或 AI）

**关键约束**：
- 每个任务必须有具体交付物
- 每个 Exit Gate 必须有可执行命令
- 每个 Stage Gate 必须有验收人签署位
- 预研任务前置
- 变更任务必须有回滚方案

## 八、快速示例

**用户说**：帮我拆解"给现有用户系统加双因素认证"。

**Step 0 判断**：功能开发 + 涉及安全，属于中风险功能。

**Step 1 边界**：
- 目标：用户登录时增加 TOTP 二次验证
- 不做：SMS 验证、硬件密钥、备用码（后续迭代）
- 约束：必须支持现有用户渐进启用、必须可回滚

**Step 2 阶段**：
- Phase 1：协议与存储设计（接口先行）
- Phase 2：后端实现（TOTP 生成/校验）
- Phase 3：前端接入（扫码/输入/启用流程）
- Phase 4：迁移与灰度（渐进启用 + 回滚预案）

**Step 3-4 任务**（示例）：
- P1.1 设计 TOTP 协议（0.5d）
- P1.2 设计存储 Schema（0.5d）
- P2.1 实现 TOTP 生成（1d）
- P2.2 实现 TOTP 校验（1d）
- ...（每任务带门禁）
- P4.1 编写回滚脚本（0.5d）← 变更任务必须有回滚方案

**Step 5 验收**：
- 命令通道：`pnpm test auth:2fa`
- 可视化通道：管理后台显示"已启用 2FA 用户数"
- 一键脚本：`verify-2fa.ps1`

**Step 6 自查**：
- 预研前置？TOTP 库选型作为 P1 前置 ✅
- 回滚方案？P4.1 ✅
- 边界/异常？P2.2 含"时间窗口偏差"用例 ✅
