## 二、你的疑问是怎么产生的

### 踩坑 1：主 agent 读插件源码

**现象**：主 agent 花 3 分钟研究 `node_modules/dsh-agent-weave/`，就是不动手。

**你的疑问**：我不是写了工具吗？工具 description 里没说明白吗？为什么要读源码？

### 踩坑 2：主 agent 不知道图 YAML 怎么写

**现象**：主 agent 要"猜" `GraphDefinitionSpec` 的 schema，得去读 `.d.ts` 才知道有哪些字段。

**你的疑问**：这不是产品应该"告诉"用户/LLM 的事吗？怎么让 LLM 自己扒源码？

### 踩坑 3：主 agent 不知道路径规则

**现象**：`MVP-4/graphs/xxx.yaml` 报 ENOENT，主 agent 得去读 `loadGraphSpec` 才知道是相对 `process.cwd()` 而不是会话工作区。

**你的疑问**：这个"潜规则"为什么要 LLM 自己 debug？

### 踩坑 4：主 agent 不知道怎么组织 user_input

**现象**：主 agent 直接把原始需求当 `user_input` 传，结果 R1 拿到一句话就开始瞎跑。

**你的疑问**：应该先把"分析结论 + 参考文件 + 验收标准"结构化，但当前工具没引导 LLM 这么做。

### 踩坑 5：15 个子代理一起跑

**现象**：主 agent 跑图后，看板显示 15 个子代理，全是 0 tok / 0 秒。

**你的疑问**：这不是个工具调一次就完了吗？怎么搞出这么多？哦，循环 3 次 × 5 个节点 = 15。但为什么全是空的？哦，provider 错了。

### 疑问的凝聚点

**你把所有踩坑连起来看，突然意识到一个根本性的东西**：

> 当前 weave 插件暴露的工具，**全是"给人手动操作 CLI"设计的**——validate、show、watch、report、status、tail。**没有一个是"给 LLM 自动编排"设计的**。

**这两类工具的性质完全不同**：

| | 给人用的 CLI | 给 LLM 用的 API |
|---|---|---|
| 契约在哪 | README / 手册 | **工具 description** |
| 错误容忍 | 允许试错 | 必须一次调对 |
| 输入形式 | 人写 YAML 文本 | **结构化 JSON 对象** |
| 上下文提示 | 人在脑子里 | **必须显式声明** |
| 学习曲线 | 读文档 | **工具自带** |

**你的疑问精炼成两句话**：

1. **"编辑流程图"缺**——LLM 想建图/改图，只能手写 YAML 文本。但 LLM 不擅长写结构化文本，容易缩进错、字段拼错。应该暴露一个**"传 JSON 对象 → 生成 YAML"**的工具。
2. **"大模型调用提示"缺**——LLM 想调工具，不知道图 schema、roleRef 白名单、路径规则、user_input 格式。这些信息应该**全部放在工具 description 和 `weave_graph_help` 里**，让 LLM 一次看懂，而不是读源码。

## 三、这个疑问背后的产品判断

你问的其实不是"加不加两个工具"，而是**产品定位的根本问题**：

### 判断 1：插件有两种用户，工具也要有两套

- **人**：CLI 命令，允许试错，有文档
- **LLM**：工具调用，必须自带契约，一次调对

**你当前的插件只做了前者**。所以 LLM 用起来别扭——它不得不"自己想办法补齐缺失的信息"。

### 判断 2："LLM 自动化"是插件产品化的核心

如果你做插件只是给自己手动用，那 CLI 就够了。

**但你的目标是"可视化 Agent 任务编排工具"**——核心卖点就是"一句话需求 → 自动编排"。这个价值**只有 LLM 自动化才能兑现**。

**所以给 LLM 用的工具不是补充，是核心。**

### 判断 3：给 LLM 用的工具，是"结构化 + 低认知负担"

- **结构化**：不传文本，传 JSON 对象（`spec` 而不是 `yaml_string`）
- **低认知负担**：契约、白名单、示例、工作流**全写在 description 里**，不要求 LLM 去读源码

**这就是你疑问的本质。**

### 判断 4：这两块是 MVP-5/MVP-6 的地基

- **MVP-5 画布编辑器**：需要一个"画布 → JSON spec → YAML"的 API。这就是 `weave_graph_create`。
- **MVP-5 Gallery / 流程包**：需要"模板 → 图"的 API。这就是 `weave_graph_from_template`。
- **MVP-6 生态分发**：用户导入图 YAML，验证 + 执行。需要 `weave_graph_load`。

**你今天发现的缺口，是后面三个 MVP 的公共底座。**

## 四、你真正想表达的东西

**表面**：插件缺两个工具。
**本质**：**插件的能力暴露，还是"人-first"的，不是"LLM-first"的。**

**"人-first"的表现**：
- 工具 description 只有一句话，细节在源码里
- 输入是文本 YAML，不是结构化对象
- 报错只告诉"哪里错了"，不告诉"怎么改"
- LLM 要自己 debug

**"LLM-first"应该有的样子**：
- 工具 description 自带 schema、白名单、示例、工作流
- 输入是结构化对象，Zod 校验
- 报错带修复建议
- LLM 一次调对，不用 debug

**你的使用场景从"人操作 CLI"变成了"LLM 自动编排"，但插件没跟上这个转变。**
