## 一、严重问题（S 系列 · 13 个）

### 🔴 S1：state-graph 硬编码 `graphVersion` 与空 `graphSchemaHash`

**位置**：`state-graph.ts` L191、L259

**根因**：T1 类型定义时 `RunOptions` 未包含这两个字段，开发时占位。但 `checkpoint.restoreFromLatestCheckpoint` 已用它们比较，导致版本感知恢复形同虚设。

**影响**：所有 checkpoint 写入相同版本，版本迁移路径从未被触发。MVP-3 引入多版本后首次触发即崩。

**修复**：
```typescript
// RunOptions 增加必需字段
export interface RunOptions<T> {
  checkpoint: CheckpointCallback<T>
  graphVersion: string          // 新增（必需）
  graphSchemaHash: string       // 新增（必需）
  agent?: Agent
  signal?: AbortSignal
  initialIteration?: number
}

// run() 中校验
if (!options.graphVersion) throw new Error('RunOptions.graphVersion 是必需的（RES.8 §三.1）')
```

**阻塞 MVP-3**：✅

### 🔴 S2：chain-runner `signal` 是假中止，STOP 只在阶段边界

**位置**：`chain-runner.ts` L181、L222

**根因**：MVP-1 用最简单的阶段边界检查，`new AbortController().signal` 每次创建但从不 `abort()`。

**影响**：用户创建 STOP 后要等当前角色跑完（R6 曾 650s），期间持续烧 token。**Token 浪费主因**。

**修复（修正版）**：**注意 `ctx.effect` 返回 disposer，不是 fn 的返回值**（Cordis 官方文档明确）：
```typescript
// ✅ controller 在 effect 外部创建
const ctrl = new AbortController()
const stopWatcher = setInterval(() => {
  if (existsSync(stopFlagPath(productionsRoot))) {
    ctrl.abort(new Error('用户 STOP'))
  }
}, 1000)

const dispose = ctx.effect(() => () => {
  clearInterval(stopWatcher)
  if (!ctrl.signal.aborted) ctrl.abort()
})

try {
  for (const step of steps) {
    if (ctrl.signal.aborted) break
    const run = await ctx.subagents.start(step.roleId, {
      prompt: [...],
      signal: ctrl.signal,   // 真实 signal
    })
  }
} finally {
  clearInterval(stopWatcher)
  dispose()
}
```

**阻塞 MVP-3**：✅

### 🔴 S3：chain-runner `setInterval` 未用 `ctx.effect()` 注册

**位置**：`chain-runner.ts` L216

**根因**：MVP-1 写这段时还没有资源生命周期契约。`finally` 不覆盖进程强杀或热重载。

**影响**：热重载后心跳定时器累积泄漏。

**修复（修正版）**：**注意 `ctx.effect` 是插件级生命周期，不是执行级**。每次 runChain 注册 effect 会累积。应该用**插件级 heartbeat 集合**：
```typescript
// 插件级：注册一个集合 + 一个 effect
const activeHeartbeats = new Set<NodeJS.Timeout>()
ctx.effect(() => () => {
  for (const t of activeHeartbeats) clearInterval(t)
  activeHeartbeats.clear()
})

// runChain 内：
const heartbeat = setInterval(...)
activeHeartbeats.add(heartbeat)
try { ... } finally {
  clearInterval(heartbeat)
  activeHeartbeats.delete(heartbeat)
}
```

**阻塞 MVP-3**：✅

### 🔴 S4：state-graph `loopUsed` 恢复后归零

**位置**：`state-graph.ts` L176

**根因**：`const loopUsed = new Map<string, number>()` 每次 run 新建，未考虑恢复场景。

**影响**：loop 边 `maxIter: 3` 已用 2 次 → checkpoint → 恢复 → loopUsed 空 → 又可回退 3 次 → **无限循环风险**。

**修复（修正版）**：**不要把内部状态塞进用户 State**，通过 checkpoint 落盘引擎内部状态：
```typescript
// 1. 扩展 CheckpointPayload
interface CheckpointPayload<T> {
  // ...
  loopUsage?: Record<string, number>   // 引擎内部状态
}

// 2. checkpoint 时落盘
await options.checkpoint({ ..., loopUsage: Object.fromEntries(loopUsed) })

// 3. 恢复时读回
const restored = await restoreFromLatestCheckpoint(...)
if (restored && 'loopUsage' in restored) {
  loopUsed = new Map(Object.entries(restored.loopUsage))
}
```

**阻塞 MVP-3**：✅

### 🔴 S6：state-graph 条件边 `used` 无上限

**位置**：`state-graph.ts` L288

**根因**：`addConditionalEdge` 的 `maxIter` 是可选参数，设计假设"条件边自己会返回 END"，但条件边形成环时不会。

**影响**：条件边 A→B + B→A 形成环（非 loop 类型），会死循环。

**修复**：`addConditionalEdge` 强制 maxIter 默认值（= 全局 maxIterations）。

### 🔴 S7：graph-service `fromDefinition` 完全没处理 cond 边

**位置**：`graph-service.ts` L95-105

**根因**：`state-graph` 的 `addConditionalEdge` 接受**函数**，YAML 里是**字符串 when**，两者间需要一个"字符串 → 函数"的转换层，被遗漏。

**影响**：用户从 YAML 加载含 cond 边的图，**cond 边静默失效**。**MVP-2 门禁"图支持条件分叉"实际未达成**。

**修复（修正版）**：**`'__CONTINUE__'` 不在 ConditionHandler 契约内**。正确做法是**所有 cond 边合成一个 ConditionHandler**：
```typescript
const condEdgesByFrom = groupBy(parsed.edges.filter(e => e.type === 'cond'), e => e.from)
for (const [from, condEdges] of condEdgesByFrom) {
  graph.addConditionalEdge(
    from,
    async (state) => {
      for (const edge of condEdges) {
        if (evaluateCondition(edge.when, state)) return edge.to
      }
      return END   // 都不满足 → 终止
    },
    Math.max(...condEdges.map(e => e.maxIter ?? 1)),
  )
}
```

**阻塞 MVP-3**：✅

### 🔴 S8：审批门 fail-open（approval 服务缺失时静默跳过）

### 🔴 S9：state-graph `emit` 事件从不落盘

**位置**：`state-graph.ts` L167-170

**根因**：MVP-2 设计时，"事件流"和"checkpoint 落盘"是两个独立机制。`checkpoint` 只落 state。

**影响**：进程退出或崩溃后，trajectory **全丢**。用户想看"执行到哪一步失败"无数据。

**修复（修正版）**：**`artifactsRoot` 需从参数传入，且用流式写入避免阻塞**：
```typescript
// createStateGraph 增加 artifactsRoot 参数
export function createStateGraph<T>(
  ctx: Context,
  maxIterations = 25,
  maxConcurrentChildren = 8,
  artifactsRoot?: string,   // 可选，不传则不落盘
): StateGraph<T>

// run() 惰性初始化 trace 流
let traceStream: fs.WriteStream | null = null
function ensureTraceStream() {
  if (traceStream || !artifactsRoot) return
  const traceDir = join(artifactsRoot, 'traces')
  mkdirSync(traceDir, { recursive: true })
  traceStream = fs.createWriteStream(join(traceDir, `${graphId}.jsonl`), { flags: 'a' })
  ctx.effect(() => () => traceStream?.end())
}

// emit 用异步写入
const emit = (event) => {
  trajectory.push(event)
  ctx.emit(event.type, event)
  ensureTraceStream()
  if (traceStream) traceStream.write(JSON.stringify(event) + '\n')
}
```

**阻塞 MVP-3**：✅

### 🔴 S11：state-graph 无出边时静默当成功

**位置**：`state-graph.ts` L319-323

**根因**：`next === END`（显式终止）和 `next === undefined`（无出边）被同一个分支处理，都返回 `success: true`。

**影响**：图执行到死胡同（无出边）会被**误判为成功**。

**修复（修正版）**：**不要改变现有行为，只加 warning 事件**（避免破坏"末端节点即终点"的用法）：
```typescript
if (next === undefined) {
  emit({
    type: 'graph/error',
    graphId, node: current, timestamp: Date.now(),
    data: { error: `节点 "${current}" 无出边，按正常结束处理`, level: 'warning' },
  })
  break
}
```

### 🔴 S12：atomic-merge 原型污染漏洞

**位置**：`atomic-merge.ts` L44-62

**根因**：`Object.entries(patch)` 会包含 `__proto__` 键，赋值 `result['__proto__']` 会污染对象原型。

**影响**：如果 `patch` 来自用户输入（YAML/LLM 输出），攻击者可注入 `__proto__` 污染整个状态对象。

**修复（修正版）**：**用无原型对象，而非过滤列表**：
```typescript
// 结果对象无原型 → 即使 patch 有 __proto__ 也不会污染
const result: Record<string, unknown> = Object.assign(Object.create(null), prev)

for (const [key, patchValue] of Object.entries(patch)) {
  // 不需要过滤——Object.create(null) 的对象没有原型可以污染
  // ...
}

// 返回给调用方前转回普通对象
return { success: true, state: { ...result } as T }
```

**阻塞 MVP-3**：✅

### 🔴 S13：可视化数据源断裂（直接影响你的验收）

**位置**：`event-bus.ts` L89-102（读 `data.tokenUsed` / `data.retryCount`）、`html-report.ts` L39-45（读 `data.inputTokens` 等）、`state-graph.ts` L238-245（emit `node-end` 时**没有 data 字段**）

**根因**：`node-end` emit 时，这些数据没有被提取出来放进 `data`。结果：可视化层读到的 Token 和 retry 永远是 0。

**影响（直接关系到你的验收）**：
- 终端实时视图：`Token: 0`、`retry: 0/3` 永远是 0
- HTML 报告的 Token 分账表**永远是空的**
- 只有 `graph-visual-commands.ts` 的 mock 模式能看到数据
- **真实 LLM 环境下，你会看到"执行完了但 Token 显示 0"**

**修复（修正版）**：**给 `GraphNodeContext` 加上报 API**：
```typescript
interface GraphNodeContext<T> {
  // ...
  /** 节点执行时上报 token 用量（引擎汇总到 node-end 事件） */
  reportTokenUsage?(usage: { input: number; output: number; cacheRead?: number }): void
  /** 节点执行时上报 retry（用于可视化） */
  reportRetry?(count: number): void
}

// 引擎侧：
let pendingUsage: { input: number; output: number; cacheRead: number } | null = null
let pendingRetry: number | null = null

const nodeCtx: GraphNodeContext<T> = {
  // ...
  reportTokenUsage(usage) { pendingUsage = { input: usage.input, output: usage.output, cacheRead: usage.cacheRead ?? 0 } },
  reportRetry(count) { pendingRetry = count },
}

// node-end 时合并进 data
emit({
  type: 'graph/node-end',
  // ...
  data: {
    ...(pendingUsage ? {
      inputTokens: pendingUsage.input,
      outputTokens: pendingUsage.output,
      cacheReadTokens: pendingUsage.cacheRead,
      tokenUsed: pendingUsage.input + pendingUsage.output,
    } : {}),
    ...(pendingRetry !== null ? { retryCount: pendingRetry } : {}),
  },
})
```

## 二、Windows 环境专项问题（新增 WIN 系列）

### 🪟 WIN1：`checkpoint.ts` 用 `lastIndexOf('/')` 在 Windows 上脆弱

**位置**：`checkpoint.ts` L76

```typescript
const dir = fullPath.slice(0, fullPath.lastIndexOf('/'))
```

**根因**：`dir(graphId)` 返回 `${this.root}/checkpoints/${graphId}` —— 用 `/`。但在 Windows 上如果 `root` 是 `C:\foo`，混用分隔符可能引发问题。如果未来用 `path.join` 重构（会生成 `\`），`lastIndexOf('/')` 返回 -1 → `dir` 为空。

**Windows 实测依据**：Node.js 官方建议使用 `path.join` / `path.normalize` 而非硬编码分隔符。

**修复**：
```typescript
import { dirname, join } from 'node:path'

// dir() 用 join 保证平台正确
dir(graphId: string): string {
  return join(this.root, 'checkpoints', graphId)
}

// write() 用 dirname 替代 lastIndexOf('/')
write(fullPath: string, record: CheckpointRecord): Promise<void> {
  const dir = dirname(fullPath)   // 跨平台安全
  mkdirSync(dir, { recursive: true })
  // ...
}
```

**阻塞 MVP-3**：建议修（Windows 环境必须）

### 🪟 WIN2：`dsh plugin add` 路径含空格会被拆断

**位置**：插件安装脚本（`test-env/` 相关）

**根因**：`apps/cli/src/plugin.ts` 调用 `spawnSync('pnpm', args, { shell: process.platform === 'win32' })`。在 Windows 上 `shell: true` + CMD，Node 设置 `windowsVerbatimArguments`，argv 被拼接为一个未加引号的命令行，cmd 重新分词。

**影响**：路径含空格的插件安装会失败，打印误导性的 warning。

**修复**：**将插件包放在无空格路径下**，或等待官方修复（Discussion #2485 已有补丁方案）。

**阻塞 MVP-3**：✅（影响安装流程）

### 🪟 WIN3：ESM 动态 import 不接受 Windows 裸路径

**位置**：`graph-visual-commands.ts` L85

```typescript
const { evaluateCondition } = await import('../l2-engine/condition-edge.js')
```

**根因**：Node.js ESM 动态 `import()` 不接受裸 Windows 路径（如 `C:\path\to\manifest.js`），只允许 `file://` URL。虽然这里的相对路径 `../` 通常没问题，但如果构建产物中的路径解析出意外情况，在 Windows 上可能报 `ERR_UNSUPPORTED_ESM_URL_SCHEME`。

**修复**：
```typescript
import { pathToFileURL } from 'node:url'
const { evaluateCondition } = await import(
  pathToFileURL(join(__dirname, '../l2-engine/condition-edge.js')).href
)
```

**阻塞 MVP-3**：建议修

6. **WIN2 插件路径含空格**——Windows 安装失败

- S2/S3：`ctx.effect` 返回 disposer，不是 fn 返回值
- S4：内部状态不塞进用户 State，通过 checkpoint 落盘
- S7：`'__CONTINUE__'` 非法，用"所有 cond 边合成一个 handler"
- S8：加 `required` 字段区分 fail-closed 和 fail-open
- S9：`artifactsRoot` 从参数传入，用流式写入
- S12：用 `Object.create(null)` 而非过滤列表
- M9：排队版 release 不要先 `active--`
- WIN1：用 `path.dirname` 替代 `lastIndexOf('/')`
