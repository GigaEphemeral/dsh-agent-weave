## 一、调研结论摘要

**核心发现**：自进化多 Agent 系统在 2026 年已从学术概念走向工程落地，形成了“**观察→提议→验证→应用→回滚**”的标准闭环。DSH 生态已有多个可直接复用或借鉴的自进化插件，其设计理念与我们的需求高度吻合。

**三条关键结论**：

1. **自进化的核心不是“让 Agent 自由修改自身”，而是构建受控闭环**——记录轨迹、有界提议、沙箱验证、确定性回滚。没有选择压的进化只是随机生成。

2. **进化对象分四层**：角色 Skill、角色配置、流程拓扑、观察者策略。学术前沿已覆盖全部四层，工程落地以 Skill 和配置为主，流程拓扑正在成熟。

3. **DSH 生态已具备自进化的基础设施**：Cordis 的热重载能力 + 插件化架构 + 可追溯的 Session 日志，天然支撑“可组合、可审查、可持续改进”的进化闭环。

## 三、核心机制深度分析

### 3.1 流程拓扑进化（DAG 优化）

**目标**：让 StateGraph 从执行轨迹中学习，自动调整图的拓扑结构。

**AgentFlow 的完整闭环**（最成熟的工程参考）：

```
自然语言目标 → 白名单奖励配置 → 工作流版本 → DAG 实际执行 → 严格业务评分
                                                                    ↓
                                              训练失败反思与示例回放
                                                                    ↓
                                              指令与拓扑候选池 → 神经 Embedding + GP/EI
                                                                    ↓
                                              独立验证集 → 版本产物与回滚 DSL
```

**关键设计约束**：
- 每轮生成 3 个候选，只评估 2 个；两轮共评估 4 个新候选
- **测试集不参与变异或选版**（独立验证集是硬约束）
- 进化对象：节点指令、训练经验示例、受限 DAG 拓扑
- 结构搜索可在单节点、路由/优先级双专家、初判后复核之间选版，**不等同于任意图生成**

**FlowScout 的流程挖掘方法**：
1. **Workflow Miner**：从历史编排日志中挖掘频繁工具协调骨架（PM4Py 流程挖掘）
2. **Workflow Executor**：编译为可执行形式，在优化集和验证集上运行
3. **Workflow Optimizer**：基于执行反馈，用蒙特卡洛树搜索精炼拓扑

**MANTA 的推理时拓扑自适应**：
- 执行前从历史结构经验初始化任务条件拓扑
- 执行中监控协作轨迹，当当前组织不足时应用有界结构更新
- 可修改：Agent 角色、通信链接、执行顺序、信息可见性、验证路径

**Pragmos 的流程模型发现**：
- LLM 生成执行路径列表 → 揭示因果、冲突和并发关系
- 构建直接跟随图（DFG）→ 排序关系图 → 模块分解树 → BPMN 流程模型

### 3.2 角色 Skill 进化

**目标**：让每个角色的 Skill 文档从执行反馈中持续优化。

**SkillGrad 的核心方法**：

```
Skill 包 = 结构化参数（可优化对象）
执行轨迹 = 轨迹级损失证据
自动诊断 = 文本梯度（指示修正方向）
动量代理 = 累积反复出现的诊断模式到持久化记忆覆盖层
Patcher Agent = 执行层感知编辑，应用到 Skill 包
```

**SkillGrad 的实验结果**：在 SpreadsheetBench Verified 和 WikiTableQuestions 上，相比最强的训练基线平均提升 **6.7 个百分点**；消融实验表明动量和对比诊断都对最终 Skill 质量有贡献。

**FlowEvo 的 Skill 策展机制**：
- 工作流→技能编译：从成功轨迹中提取可复用可执行工件
- 技能→工作流反馈：通过直接执行或结构化上下文注入支持未来问题解决
- **技能策展**：监控下游效用，抑制导致负迁移的技能

### 3.3 角色配置进化

**目标**：调整角色的工具集、质量门、Token 预算、生命周期、模型路由。

**AgentFlow 的进化对象**包含“节点指令、训练经验示例与受限 DAG 拓扑”，模型权重不变。这对应到我们的系统：

| 配置项 | 变异方向 | 验证指标 |
|---|---|---|
| `tools` | 增加/减少工具 | 该角色任务成功率变化 |
| `quality_gate` | 调整阈值 | 首次通过率 vs 返工率 |
| `token_budget` | 调整预算 | Token 消耗/成功交付 |
| `lifecycle` | resident↔on-demand | 冷恢复延迟 vs 资源占用 |
| `model` | 切换模型 | 质量/成本权衡 |

### 3.4 观察者策略进化

**目标**：优化观察者的 `criteria`、`dispatch_conditions`、`token_budget`。

观察者策略的进化可以基于误报率/漏报率：
- 误报率过高 → 提高触发阈值或减少 criteria
- 漏报率过高 → 降低触发阈值或增加 criteria
- Token 消耗过高 → 调整 dispatch_conditions，降低观察频率

### 4.3 五步进化闭环

参考 `dsh-auto-evolve` 的完整闭环设计：

**Step 1：Observe（观察）**

- 监听 `tools/result` 和 `agent/request-error` 事件
- 记录去重信号：工具失败、无进展重复、请求错误
- 信号写入 RunLedger（复用已有审计账本）
- 触发条件：阈值跨越（如连续失败 ≥ 3 次、同一节点在相同位置失败 ≥ 3 次）

**Step 2：Propose（提议）**

- 有界循环：快照 genome + 最近观测 → 调用 `ctx.llm.stream()` 生成变异候选
- **封闭变异词汇表**：LLM 只能填充通过 Zod Schema 校验的 payload，不能发明新的资产类型或操作符
- 操作符：`add` / `patch` / `retire`
- 资产类型：`skill` / `role_config` / `graph_edge` / `observer_config`
- 内容指纹去重：已匹配待验证候选的变异被丢弃

**Step 3：Validate（验证）**

- 在沙盒子代理中回放失败片段
- 一次不带候选变异（基线），一次带候选变异（试验）
- 对比指标：完成度、工具失败数、工具调用成本、Token 消耗
- **验证即部署**：同一个 mutation applier 用于验证和正式应用
- **测试集不参与变异或选版**

**Step 4：Apply（应用）**

- 验证通过且人工审批后，提升为 live genome
- 技能通过 `ctx.skills.register()` 注册（立即可见）
- RunLedger 记录应用，保留前序内容
- disposer 保留用于回滚

**Step 5：Rollback（回滚）**

- 回归时注销 live 贡献，恢复父内容为新的候选
- 写入 `rollback` ledger 条目
- 插件卸载时所有 live 注册被拆除

### 4.4 安全边界（硬约束）

| 边界 | 实现 | 参考来源 |
|---|---|---|
| **封闭变异词汇表** | LLM 只能填充通过 Zod Schema 的 payload | dsh-auto-evolve |
| **执行验证而非自我声明** | 候选必须在沙盒中可观测指标优于基线 | dsh-auto-evolve / AgentFlow |
| **成本封顶** | `maxCostPerCycle` / `dailyBudget` | dsh-auto-evolve |
| **回滚一等公民** | 每次应用保留 disposer + 父内容 | dsh-auto-evolve |
| **默认 observe-only** | 默认只观察和提议，不自动应用 | dsh-auto-evolve |
| **提议需人工审阅** | 所有变异候选进入待审阅队列 | dsh-evolve-modes |
| **独立验证集** | 测试集不参与变异或选版 | AgentFlow |
| **动量机制** | 反复诊断模式累积到持久化记忆，避免重复犯同类错误 | SkillGrad |
| **评分标准隔离** | 回归任务评分标准物理上不进入 agent 上下文 | dsh-darwin |
| **零代码执行优先** | MVP 只启用 config 和 skill 级合成；code 级默认关闭 | dsh-darwin |
| **证据逐字约束** | 提议的证据必须逐字来自用户消息 | dsh-evolve-modes |

### 4.5 与 RunLedger 的集成

RunLedger 是自进化的数据基础。在现有 RunLedger 事件流基础上，增加以下事件类型：

```typescript
interface EvolutionEvent {
  type: 'observe' | 'propose' | 'validate' | 'apply' | 'rollback';
  evolution_id: string;
  genome_asset: string;        // 被进化的资产 ID
  mutation_type: 'add' | 'patch' | 'retire';
  baseline_metrics?: {         // 验证时的基线指标
    completion: number;
    tool_failures: number;
    token_cost: number;
  };
  trial_metrics?: {            // 验证时的试验指标
    completion: number;
    tool_failures: number;
    token_cost: number;
  };
  improvement?: number;        // 提升幅度
  approved_by?: string;        // 审批人
  timestamp: number;
}
```

## 五、关键风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| **进化不稳定** | 候选在验证集上提升但在生产环境退化 | 独立验证集 + 人工审批 + 回滚一等公民 |
| **Token 消耗失控** | 每次进化周期消耗大量 Token | `maxCostPerCycle` / `dailyBudget` 封顶 |
| **变异空间爆炸** | LLM 生成大量无效候选 | 封闭变异词汇表 + Zod Schema 校验 + 指纹去重 |
| **进化与人工冲突** | 自动进化覆盖人工修改 | 版本化 ledger + 冲突提示 + 人工审批 |
| **负迁移** | 某次进化导致其他任务退化 | FlowEvo 的技能策展机制（监控下游效用） |
| **测试集污染** | 变异过程“看到”了测试集 | 测试集不参与变异或选版（硬约束） |
| **Cordis 热重载竞态** | 进化应用时热重载导致资源泄漏 | 所有资源 `ctx.effect()` 注册 + 热重载测试入门禁 |


## 六、总结

**自进化与自优化是这套编排工具的“最后一公里”** 。核心设计要点：

1. **五步闭环**：Observe → Propose → Validate → Apply → Rollback。所有进化产物必须经过独立验证和人工审批才能生效。

2. **四层进化对象**：角色 Skill、角色配置、流程拓扑、观察者策略。学术前沿（TPGO/ANN/HiVA/SkillGrad/FlowEvo/MANTA）已覆盖全部四层，工程落地以 Skill 和配置为主。

3. **验证是硬约束**：候选必须在沙盒中可观测指标优于基线，测试集不参与变异或选版。AgentFlow 的实证表明，“闭环可运行，收益尚不稳定”——进化系统本身需要持续调优。

4. **安全边界不可协商**：封闭变异词汇表、成本封顶、回滚一等公民、默认 observe-only、提议需人工审阅。

5. **DSH 生态已具备完整参考**：`dsh-auto-evolve`（最完整五步闭环）、`dsh-evolve-modes`（可组合模式 + 人工审阅）、`dsh-darwin`（双插件 + 评测门 + 确定性回滚）、`harness-self-evolution-plugin`（全盘扫描 + 13 MCP 工具）。

6. **MVP 集成路径**：Phase 3 打数据基础 → Phase 4 可视化信号 → Phase 5 分发渠道 → Phase 6 完整实现。预估工时约 22 天，主要集中在 Validate（沙盒验证）和 Propose（候选生成）。
