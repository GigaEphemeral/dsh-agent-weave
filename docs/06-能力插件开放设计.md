## 一、最终目标与需求细化

### 1.1 一句话目标

实现一个**可视化的 Agent 任务编排工具**——用户输入一句话需求，自动拆解为工作流任务图，多角色 subagent 按图协作（含循环与条件回退），激活状态全程可视化，每个 Agent 独立记忆防污染，可互相对话，**角色与流程可对外配置、用户可自行导入创建**。

### 1.2 硬需求清单（G1-G8）

| # | 需求 | 一句话验收 |
|---|---|---|
| G1 | 任务拆分 + 工作流 | 一句话需求 → 拆成工作流任务图，角色按图协作 |
| G2 | 非线性/循环编排 | 顺序 + 条件 + 循环（开发→测试→审核循环） |
| G3 | 可视化激活状态 | 谁在跑/等谁/产出啥，实时可见，可恢复 |
| G4 | 记忆纯洁性 | 每 Agent 独立记忆，只经文件/消息交接，防污染 |
| G5 | Agent 间对话 | subagent 定向对话推进交付 |
| G6 | 角色可自定义 | 导入文件创建角色 + 画图连线交互逻辑 |
| G7 | 流程可自定义 | 用户自建流水线/流程，声明式或画布方式 |
| G8 | 对外配置/插件化 | 支持第三方开发者分发角色包、流程模板、自定义节点 |

### 1.3 需求分层

```
┌─────────────────────────────────────────────┐
│ 核心层（P0）：G1-G5                          │
│ 一句话需求 → 工作流图 → 多角色协作 → 可视化    │
├─────────────────────────────────────────────┤
│ 扩展层（P1）：G6-G7                          │
│ 角色自定义 + 流程自定义                        │
├─────────────────────────────────────────────┤
│ 生态层（P2）：G8                             │
│ 对外配置 + 插件化 + 社区分发                   │
└─────────────────────────────────────────────┘
```

**核心层是产品的基础能力**，扩展层让用户从“使用者”变为“构建者”，生态层让平台从“工具”变为“生态”。三层递进，但**声明式格式（YAML/JSON）应从第一天就定好**，后续扩展才不会返工。


## 二、市场现状与产品分类

### 2.1 产品分类图谱

| 族 | 代表 | 形态 | 谁定义工作流 | 角色自定义 | 流程自定义 | 对外插件 |
|---|---|---|---|---|---|---|
| **A. 编排框架/库** | LangGraph、CrewAI、OpenAI Agents SDK | 代码 SDK | 开发者写代码 | 代码定义 | 代码定义 | 代码扩展 |
| **B. 可视化编排平台** | Dify、Coze、n8n、Langflow | 画布/低代码 | 用户在画布拖拽 | UI 定义 | 画布连线 | 插件市场 |
| **C. 编码助手内建 Agent 团队** | Claude Code subagents、DSH agentTeams | 宿主内建 | 配置文件/preset | 配置文件 | preset 定义 | 有限 |
| **D. 软件工程专用多 Agent 团队** | MetaGPT、ChatDev | 代码 SDK + SOP | 框架内置角色与流程 | 硬编码 | 硬编码 | 无 |

**定位判断**：本工具横跨 **B（可视化画布）+ C（复用 DSH 原生 subagent 执行）** ，并在 D 族（软件工程专用团队）的经验基础上进行扩展。核心差异化在于：**编排单元是“带 skill/persona 的 subagent”，而非通用 LLM 节点**。

### 2.2 关键产品实现逻辑对比

| 框架/产品 | 编排模型 | 角色自定义 | 流程自定义 | 对外插件 | 证据 |
|---|---|---|---|---|---|
| **LangGraph** | StateGraph（节点+边） | 代码定义 | 代码定义 `add_conditional_edges` | Python/TS 包 | 📘 |
| **CrewAI** | Flow（工作流）+ Crew（团队） | YAML/代码定义 Agent | Python 代码定义 Flow | 代码扩展 | 📘 |
| **AutoGen Studio** | Team Builder + Playground | 拖拽/JSON 声明式 | 拖拽/JSON 声明式 | Gallery 导入 | 📘 |
| **Dify** | 画布 DAG（LLM/工具/检索/条件/循环节点） | UI 配置角色 Prompt | 画布连线 | 插件市场 | 📊 |
| **Coze** | 工作流画布 + 多 Agent | UI 配置人设+技能 | 画布连线 | 平台内置 | 📊 |
| **n8n** | 通用工作流节点连线 + AI Agent 节点 | 自定义节点 | 画布连线 | 社区节点仓库 | 📘 |
| **Hermes Synapse** | 拖拽 DAG 画布（严格无环） | SVG 画布 + 隔离 Agent 聊天 | 拖拽连线 | 本地 Qdrant RAG | 📘 |

### 2.3 市场核心结论

**结论 1：图编排 + 独立 subagent + 持久化状态 是领域公认架构**。LangGraph 的 StateGraph、Dify 的画布 DAG、Hermes 的拖拽 DAG 画布都验证了这一方向。

**结论 2：记忆隔离的行业标准答案是“独立 context window + 文件交接”** 。Claude Code subagents 明确“每个 subagent 以全新的、隔离的上下文窗口启动”，DSH 原生 subagent 天然具备这一能力。

**结论 3：你的核心差异化不是“多 Agent 团队”，而是“画布可编排的 Agent 团队 + 对外可配置的生态”** 。MetaGPT/ChatDev 的角色和 SOP 是硬编码的，Dify/Coze 的编排单元是通用 LLM 节点。**“DSH 原生的、角色技能驱动的、画布可编排的、对外可配置的 Agent 团队”——四者交集处目前没有成熟产品。**

**结论 4：最难复刻的是 Dify/Coze 的画布编辑体验和插件市场生态**。建议拆成独立里程碑：只读看板先行（MVP-4），拖拽编辑器后置（MVP-5），社区分发最后（MVP-6+）。


## 三、DSH 能力底座现状

### 3.1 已确认的四层编排能力

源码核查确认，DSH 仓库里已有四套协作/编排服务：

| 层 | 包 | 成熟度 | 一句话 |
|---|---|---|---|
| **执行原语** | `packages/subagent/…` | **核心稳定** | 父子树 + continuable + `SubagentProvider`（角色身份）+ 记忆隔离开关 |
| **团队抽象** | `packages/experimental/agent-team` | **experimental** | lead+teammate + 任务看板（DAG）+ 持久邮箱 |
| **编排引擎** | `packages/workflow/…` | **正式 client 目录** | 脚本式编排 + worker 隔离 + chat 可视化 |
| **目标/任务** | `packages/goal/` + `packages/jobs/` | **核心稳定** | 目标跟踪（`ctx.goals`）+ 后台任务注册（`ctx.jobs`） |

### 3.2 记忆能力缝

DSH 官方在 Discussion #1638 中提出了 `ctx.memory` 的能力缝设计，核心原则是 **“没有自动系统提示注入，Agent 自己决定何时保存/召回”** 。这意味着记忆的读写时机、内容和粒度，**完全由编排层（L2/L3）控制**。

社区已有多个分层记忆插件可参考设计逻辑：`dsh-memory-db`（项目级记忆数据库，三态分类智能注入）、`evo-subagent`（每 Agent 独立 `prefercmd.md` 和 `memory.md` 知识文件）、`dsh-layered-memory`（瞬时/情景/语义三层）、`dsh-memento`（global/workspace × user/agent 分层）。

### 3.3 不可用的能力

- **experimental agent-team**：不支持循环工作流，实测不兼容 DSH 0.1.5-rc.2。
- **社区团队插件**：版本检测均不匹配 0.1.5-rc.1。
- **subagent 并发上限**：`dsh-subagent` 代码中无任何数量/并发上限，实测发生过 56 个子代理导致进程 2.2GB 内存、单核满载 20 分钟的案例。


## 四、能力差异分析

### 4.1 需求 ↔ 官方能力覆盖映射

| 需求 | 官方覆盖度 | 说明 |
|---|---|---|
| G1 任务拆分 + 工作流 | ✅ | 每角色一 `startContinuable` child |
| G2 循环工作流 | ❌ **缺失** | subagent 无内置循环/条件路由 → 自研 L2 StateGraph |
| G3 可视化激活状态 | ❌ **缺失** | 自研 L4 |
| G4 记忆隔离 | ✅ | 子代理独立 Session + `inheritsParentContext=false` |
| G5 Agent 间对话 | ⚠️ 部分 | `sendMessage` 传递，自由对话需自建路由（消息总线） |
| G6 角色动态导入 | ❌ **缺失** | 自研 L3 + YAML 加载器 |
| G7 流程自定义 | ❌ **缺失** | 自研 L2 图 DSL + 编译器 |
| G8 对外插件化 | ❌ **缺失** | 自研 L6 扩展层 |
| Token 监控 | ⚠️ 社区有 | `dsh-token-stats`（或用官方 `dsh-agent-budget`） |

### 4.2 关键差异总结

**DSH 已提供的**：角色身份（`SubagentProvider` + `persona`）、记忆隔离（`inheritsParentContext`）、持久化 Session、目标跟踪（`ctx.goals`）、后台任务（`ctx.jobs`）。

**DSH 缺失的（需自建）** ：图 DSL、StateGraph 编排引擎（含条件边/循环/熔断）、角色管理（YAML）、可视化画布、可观测性治理层、**对外配置/插件化机制**。


## 五、设计方案

### 5.1 分层架构（L0-L6）

```
┌──────────────────────────────────────────────────────────────┐
│ L6 扩展与生态层（新增）                                        │
│  角色市场 · 流程模板 · 第三方插件注册 · 社区画廊 · 导入导出       │
├──────────────────────────────────────────────────────────────┤
│ L5 可观测性与治理层                                            │
│  执行轨迹追踪 · RunLedger 审计账本 · 策略合规 · 成本熔断         │
├──────────────────────────────────────────────────────────────┤
│ L4 可视化层                                                    │
│  画布编辑器 · 实时激活状态 · Token 监控 · 观察者信号展示          │
├──────────────────────────────────────────────────────────────┤
│ L3 角色管理层                                                  │
│  YAML 配置 · 角色导入 · 观察者配置 · 生命周期与并发限制           │
├──────────────────────────────────────────────────────────────┤
│ L2 编排引擎层（自研 StateGraph）                                │
│  图 DSL · 条件边 · 循环回退 · 迭代熔断 · checkpoint · 消息总线    │
├──────────────────────────────────────────────────────────────┤
│ L1 执行与记忆层（官方 @deepseek-ai/dsh-subagent）               │
│  Continuable 子代理 · 独立 Session · 记忆隔离 · 持久化            │
└──────────────────────────────────────────────────────────────┘
```

**复用层仅 L1；自建 L2-L6。L6 是本次新增的对外配置/插件化层。**

### 5.2 核心对象模型（7 对象）

| 对象 | 定义 | 落点 |
|---|---|---|
| **Agent（角色）** | 特质 + 工具 + 模型 + 质量门 + 预算 + 观察者配置 | `R1-R10 skill`（Prompt 内容）+ `YAML` 元数据 |
| **Workflow（图）** | 节点=角色/任务，边=顺序/条件/循环/并行 | 图 DSL（JSON） |
| **Task（任务实例）** | 一句话 → 根任务 → 子任务树 | 任务树（storageDomain） |
| **State（共享状态）** | Phase / active_agent / artifacts / 质量门 / retry 计数 | `DevTeamState` |
| **Memory（角色记忆）** | 每 Agent 独立 context + 交接物 | 独立 subagent session + 工作区文件 |
| **RunLedger（运行账本）** | 不可变事件流：节点事件 + Token 分账 + 合规状态 | storageDomain（只追加） |
| **Package（角色包/流程包）** | 可导入导出的角色/流程定义（含版本、依赖） | L6 扩展层 |

### 5.3 对外配置/插件化设计（L6 核心）

#### 5.3.1 三种对外配置形态

**形态 1：角色包（Role Package）** — 用户以 YAML 定义角色，放入 `roles/` 目录即可使用：

```yaml
role_package:
  schema_version: "1.0"
  id: my-custom-role
  name: "我的自定义角色"
  author: "user@example.com"
  version: "1.0.0"
  compatible_dsh_version: ">=0.1.5-rc.1"
  role:
    system_prompt_ref: "prompts/my-role.md"
    traits: [...]
    tools: [read, write, custom_tool]
    model: { provider: deepseek-official, model: deepseek-v4-pro }
    memory_scope: private
    quality_gate: [...]
    token_budget: 50000
  prompts:
    - path: "prompts/my-role.md"
```

**形态 2：流程模板（Workflow Template）** — 用户以 YAML 定义工作流，画布可视化编辑：

```yaml
workflow_package:
  schema_version: "1.0"
  id: my-pipeline
  name: "我的开发流水线"
  author: "user@example.com"
  version: "1.0.0"
  workflow:
    nodes:
      - id: develop
        role_ref: R3-developer
        node_type: role
      - id: test
        role_ref: R4-test
        node_type: role
    edges:
      - { from: develop, to: test, type: seq }
      - { from: test, to: develop, type: cond, when: "state.quality_gate_status === 'failed'", max_iter: 25 }
  role_dependencies:
    - { id: R3-developer, version: ">=1.0.0" }
```

**形态 3：自定义节点插件（Custom Node Plugin）** — 开发者通过 DSH 插件机制注册新节点类型（如 Jira、Slack 集成节点）：

```typescript
// 注册自定义节点类型
ctx.workflowRegistry.registerNodeType('jira-action', {
  description: '调用 Jira API 创建/更新 issue',
  inputSchema: { issueKey: 'string', action: 'enum' },
  outputSchema: { success: 'boolean', issueUrl: 'string' },
  execute: async (inputs, context) => { /* 调用 Jira API */ }
});
```

#### 5.3.2 画廊（Gallery）机制

参考 AutoGen Studio 的 Gallery 设计——一个**组件集合的仓库**，用户可以导入、扩展和复用。你的 Gallery 应包含：角色包、流程模板、工具组合、提示词模板。支持文件导入、URL 导入、社区市场同步三种方式。

#### 5.3.3 社区分发

本工具本身作为一个 DSH 插件发布到 **DSH Plugin Hub**，让其他用户通过 `dsh plugin --profile web add your-plugin` 一键安装。同时构建一个**子市场**——专门用于分发角色包和流程模板，存储结构如下：

```
~/.dsh/visual-workflow/
├── roles/                  # 已安装的角色包
├── workflows/              # 已安装的流程模板
├── gallery/                # 画廊缓存（从社区市场同步）
├── combos.json             # 自定义工具组合
└── runs/                   # 运行历史
```

### 5.4 关键设计契约

| 契约 | 内容 | 敲定时机 |
|---|---|---|
| **图 DSL Schema** | `GraphDefinitionSpec`：nodes/edges/checkpoint/metadata | MVP-2 前 |
| **checkpoint 契约** | 节点级落盘，同时写入 RunLedger；Cordis 生命周期约束 | MVP-2 前 |
| **消息总线契约** | `Message` 结构 + 防死锁分级恢复 | MVP-3 前 |
| **角色 YAML Schema** | 含 `system_prompt_ref`、`lifecycle`、`max_concurrent_children` | MVP-3 前 |
| **角色包/流程包 Schema** | 含版本、依赖、兼容性声明 | MVP-3 前 |
| **Gallery 导入契约** | 文件/URL/市场三种来源 + 冲突策略 | MVP-5 前 |
| **Token 熔断契约** | 软/硬阈值 + 采集点（provider 层） | MVP-3 中 |
| **事件流契约** | OTEL 对齐 + 观察者信号写入 | MVP-4 前 |

### 5.5 观察者机制（质量保障增强）

观察者作为**正交增强层**，不改变图拓扑，与质量审核节点互补。三层观察者：L1 轻量检查（零 Token，纯函数）、L2 静默观察（低 Token，文件观察 + 分级信号）、L3 深度审查（高 Token，按需启用）。观察者信号（GREEN/YELLOW/RED）写入 RunLedger，可触发早期回退。

### 5.6 Token 优化策略

| 优化措施 | 预期效果 |
|---|---|
| `art://` 工件引用（长产出落盘，消息只传引用+摘要） | handoff 环节 Token 消耗减少 60%+ |
| System Prompt 分离不变/可变部分 + Prompt Caching | 重复注入开销降低 |
| 循环回退只传结构化 diff + 分层审核 | 循环场景 Token 消耗降低 50%+ |
| 看板推送仅含增量 | 推送开销趋近于零 |
| 复用 `dsh-agent-budget` + `dsh-discipline-guard` 做熔断 | 防止 Token 失控 |

## 七、风险、难点与待决策

### 7.1 核心难点

| 难点 | 说明 | 缓解 |
|---|---|---|
| **StateGraph 原子合并 + 并发安全** | 并行分支写同一字段的合并语义 | MVP-2 只做串行；默认 `reject-on-conflict` |
| **冷恢复延迟** | 子代理从持久化 Session 恢复的延迟 | 活跃窗口 + 10s SLA 降级人工 |
| **死锁检测** | A 等 B、B 等 A 的循环等待 | `correlation_id` + `deadline` + 分级恢复 |
| **画布 DSL 双向同步** | 画布手动编辑与 YAML 导入的冲突 | `metadata.source` 标记来源 + 冲突解决策略 |
| **并发全局上限** | dsh-subagent 无进程级并发闸 | 引擎层自建计数 + `dsh-turn-budget` 兜底 |

### 7.2 关键风险

| 风险 | 缓解 |
|---|---|
| **StateGraph 自研复杂度** | 参考 `dsh-state-graph` 逻辑（不抄码）；MVP-2 只做 seq+cond+loop |
| **循环失控 / 成本爆炸** | 迭代熔断（25）+ 硬 Token 预算 + 人工审批 + `dsh-discipline-guard` 兜底 |
| **Cordis 热重载资源泄漏** | 非 Cordis 管理资源一律 `ctx.effect()` 包装 |
| **subagent Messages 协议历史 notice 毒化** | 不依赖 subagent settlement notice 恢复；升级前归档 |
| **观察者干扰工作 Agent** | 80%+ 观察为静默文件读取；fail-open |
| **图版本化缺失** | 图 DSL 增加 `graphVersion`；参考 AgentGit/CVC |
| **对外插件的安全审计** | 参考 Dify 的 Marketplace 代码审查 + 隔离运行 + 明确权限声明 |
