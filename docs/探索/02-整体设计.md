# 可视化 Agent 任务编排工具 · 整体设计 v3

> 存档：2026-09-22｜定位：**"是什么 / 为什么 / 怎么组织"**（目标、本质、对象模型、分层、命门、演进路径）
> 权威契约与 MVP 见 `docs/04-MVP与设计契约.md`；工程实现见 `docs/05-开发契约与技术方案.md`；能力底座见 `docs/03`；市场调研见 `docs/01`


## 一、目标（是什么）

**一句话**：实现一个可视化 Agent 任务编排工具——一句话需求拆成工作流任务图，多角色 subagent 按图自动协作（含循环），激活状态全程可视化，每 agent 独立记忆防污染，可互相对话，角色可导入创建、画图连线。

**六条硬需求**：

| # | 需求 | 验收标准 |
|---|---|---|
| G1 | 任务拆分 + 工作流 | 一句话需求 → 工作流任务图，角色按图协作 |
| G2 | 非线性/循环编排 | 顺序 + 条件 + 循环（开发→测试→审核循环） |
| G3 | 可视化激活状态 | 谁在跑/等谁/产出啥，实时可见，可恢复 |
| G4 | 记忆纯洁性 | 每 agent 独立记忆，只经文件/消息交接 |
| G5 | Agent 间对话 | subagent 定向对话推进交付 |
| G6 | 角色可自定义 | 导入文件创建角色 + 画图连线 |


## 二、本质（为什么这么设计）

**本工具 = 工作流图编排运行时**。它的核心抽象是"图"，而非"对话"或"任务列表"。

这个定位来自对现状的诊断：当前系统能跑通角色协作，但本质是**人肉/线性编排**——角色顺序靠人配置，循环靠人干预，状态靠人观察。缺三样质变件：

| 缺失 | 本质 | 补法 |
|---|---|---|
| **显式图 DSL** | 工作流是数据，不是代码 | 定义 GraphDefinitionSpec，图可序列化、可版本化、可画布编辑 |
| **自动调度运行时** | 引擎驱动状态流转，而非人推着走 | 自研 StateGraph，节点只返回 `Partial<State>`，引擎原子合并 |
| **状态机 + 可视化** | 激活状态可观测、可恢复 | RunLedger 不可变事件流 + 画布实时染色 |

**关键判断**：`subagent` 是执行器（DSH 原生，天然独立记忆），我们**不自研执行层**；自建的是它之上的**图 DSL + 编排引擎 + 角色管理 + 可视化 + 可观测治理**。


## 三、核心对象模型（系统的六个基本构件）

系统的所有设计都围绕六个对象展开。它们不是并列的，而是**三层结构**——协作层定义谁和谁如何协作，执行层是协作过程中产生的具体工作，状态层记录执行过程中的数据与历史。

```
┌──────────────────────────────────────────────────────────────┐
│ 协作层（定义"谁在什么条件下和谁协作"）                          │
│                                                              │
│   Workflow（图）= Agent 之间的协作协议                         │
│     · 节点 = 角色引用（roleRef）                              │
│     · 边 = 流转条件（seq/cond/loop）                          │
│     · 定义 entryPoint、handoff 关系、质量门位置                │
│                                                              │
│   Agent（角色）= 执行者                                        │
│     · 特质 + 工具 + 模型 + 质量门 + 预算                       │
│     · 按图接受 Task、执行、可能拆解出子 Task、按图交接          │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ 执行层（协作过程中产生的具体工作）                              │
│                                                              │
│   Task（任务）= Agent 拆解出的工作单元                         │
│     · 根 Task 由用户需求产生，路由到入口 Agent                  │
│     · Agent 执行 Task 时可拆解为子 Task，指派给下游 Agent       │
│     · Task 树自然形成：根 → 子 → 孙                            │
│     · 每个 Task 有 owner（执行它的 Agent）、输入、验收标准      │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ 状态层（执行过程中的数据与历史）                                │
│                                                              │
│   State（共享状态）= Task 执行过程中的共享数据                  │
│     · Phase / active_agent / artifacts / 质量门 / retry 计数  │
│     · 引擎内存态，节点返回 Partial<State>，引擎原子合并         │
│                                                              │
│   Memory（角色记忆）= Agent 的独立记忆                          │
│     · 每个 Agent 独立 context，不共享推理过程                   │
│     · 交接只经文件（durable）+ 消息（transient）                │
│                                                              │
│   RunLedger（运行账本）= Task 执行的历史轨迹                    │
│     · 不可变事件流，只追加                                     │
│     · 支撑恢复、审计、可视化、Token 分账                        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 Agent 与 Task 的关系（核心）

**Agent 拆解 Task，Task 驱动 Agent**——这是系统的动力机制。

```
用户一句话需求
    ↓
根 Task 产生
    ↓
根 Task 被路由到入口 Agent（由图 DSL 的 entryPoint 决定）
    ↓
入口 Agent 执行根 Task：
    ├── 读取 Task 输入（用户需求）
    ├── 可能拆解出子 Task（每个子 Task 带 owner 提示、输入规格、验收标准）
    ├── 按图 DSL 的 edges 决定交接给哪个下游 Agent
    └── 输出交付物（art:// 引用）
    ↓
下游 Agent 接收子 Task，递归执行同样的过程
    ↓
Task 树自然形成：
    Task-001（需求分析，owner=R1）
      ├── Task-001.1（架构设计，owner=R2）
      │     ├── Task-001.1.1（模块拆分，owner=R3）
      │     └── Task-001.1.2（接口定义，owner=R3）
      └── Task-001.2（测试用例，owner=R5）
```

**关键设计决策**：

| 决策 | 内容 | 理由 |
|---|---|---|
| **Task 的所有权** | 每个 Task 有明确的 owner（执行它的 Agent） | 避免"多 Agent 共同负责一个 Task"导致的责任模糊 |
| **Task 的拆解粒度** | Agent 自行决定拆解深度，但受 `max_iterations` 和 Token 预算约束 | 过度拆解会导致协调开销爆炸，过浅会导致粒度太粗 |
| **Task 的验收标准** | 每个 Task 有明确的验收标准（来自 YAML 的 `quality_gate`） | 下游 Agent 按标准验收，不通过则触发回退 |
| **Task 的输入规格** | 每个 Task 明确声明需要哪些上游交付物（来自 YAML 的 `handoff.upstream`） | 避免"什么都读"导致上下文膨胀 |
| **Task 的产出形式** | 产出物落盘为 `art://` 引用，不直接在 Task 中携带内容 | 控制上下文大小，支持大产出 |

**与 Workflow 的关系**：Workflow 图定义的是 **Agent 之间的协作协议**，不是"Task 的容器"。图告诉你"R1 完成后可以交给 R2 或 R5"，但具体交给谁、拆解出什么 Task，是 R1 在执行时根据 Task 内容和图的条件边动态决定的。

**与 State 的关系**：State 是**当前活跃 Task 的共享状态**。当 Task 从一个 Agent 交接到下一个 Agent 时，State 随之流转。`active_agent` 字段标识当前哪个 Agent 在执行，`task_queue` 字段记录待执行的 Task。

**与 RunLedger 的关系**：RunLedger 记录 **Task 执行的历史轨迹**。每个 Task 的开始、完成、失败、拆解、交接都是 RunLedger 中的事件。Task 树可以从 RunLedger 重建。

### 3.2 六个对象的设计要点

| 对象 | 是什么 | 关键设计决策 | 契约位置 |
|---|---|---|---|
| **Workflow** | Agent 之间的协作协议（图 DSL） | 版本化（`graphVersion`）、静态验证、parallel 语法预留 | `04` §4.1 |
| **Agent** | 执行者 = Prompt 内容 + 结构化元数据 | YAML 元数据 + `system_prompt_ref` 指向已有 skill，**不自研 Prompt** | `04` §4.4 |
| **Task** | Agent 拆解出的工作单元 | owner 唯一、验收标准明确、输入规格声明、产出用 `art://` 引用 | `04` §4.2 |
| **State** | 当前活跃 Task 的共享状态 | 节点只返回 `Partial<State>`，引擎原子合并，冲突 `reject-on-conflict` | `04` §3.1 |
| **Memory** | Agent 的独立记忆 | 复用 subagent 的 `inheritsParentContext=false`，**不自研隔离** | `04` §4.4 |
| **RunLedger** | Task 执行的历史轨迹 | 与 State 分离；OTel 语义对齐；支撑恢复与分账 | `04` §4.2 |

**State 与 RunLedger 的分工**是设计的关键：State 是**当前快照**（可被节点改），RunLedger 是**历史轨迹**（只追加）。前者驱动引擎流转，后者支撑恢复、审计、可视化、分账。两者通过 checkpoint 回调**双写**——引擎每次合并状态后，同一回调同时落盘 State 快照和 RunLedger 事件。


## 四、分层架构（构件的组织方式）

六个对象分布在五个层次中，每层有明确的**复用/自建边界**：

```
L0 角色资产      R1-R10 skill + 3 横切纪律                 ✅ 已完成
L1 执行与记忆    官方 @deepseek-ai/dsh-subagent            🔄 复用
L2 编排引擎      自研 StateGraph                            🔨 自建
L3 角色管理      自研 YAML 配置                             🔨 自建
L4 可视化        自研画布 + 实时激活状态 + Token 监控        🔨 自建
L5 可观测与治理  RunLedger + 策略合规 + 成本熔断            🔨 自建（参考 OTel）
```

**分层设计原则**：

- **复用层仅 L1**：subagent 的记忆隔离、Session 持久化、Provider 注册是一等能力，**不自研**。
- **自建 L2-L4**：图 DSL、StateGraph 引擎、角色管理、画布是产品差异化所在，DSH 无现成。
- **L5 混合**：RunLedger 自建（业务语义），Token 熔断**复用官方 + 社区**（不自研），可观测性对齐 OTel 标准。
- **依赖方向**：L5 依赖 L2/L3/L4 的事件，L4 依赖 L2/L5 的数据，L2 依赖 L1 的执行，L3 依赖 L1 的 Provider 注册。

**L5 是 MVP-4 的前提**：没有 RunLedger 的节点级事件流，画布无法染色；没有 Token 分账，无法识别成本瓶颈。这是为什么 RunLedger 必须在 MVP-3 就落地，而非推迟到可视化阶段。


## 五、三条命门（设计的核心约束）

这三条不是功能，而是**设计约束**——它们决定了其他所有设计不能越过的边界。

### 5.1 记忆纯洁性（G4）：不共享 context，只经文件+消息交接

**约束**：任何两个角色之间**不得共享推理上下文**。

**实现方式**：复用 subagent 的 `inheritsParentContext=false`，每个角色是独立 Session。角色之间的交接只通过两条通道：
- **产出物 = 文件（durable）** ：落盘到 `productions/<角色>/`，下游只读上游产出（依 YAML `handoff.upstream`）
- **即时协商 = 消息（transient）** ：通过 `sendMessage` 定向发送，父代理中转

**行业印证**：Claude Code subagents「每个 subagent 以全新隔离 context window 启动 + 文件交接」；MetaGPT「结构化文档交接 > 自由对话防失真」。

### 5.2 角色间对话（G5）：定向 handoff，非广播

**约束**：消息是**定向的**，不是广播的；**有 deadline 的**，不是无限等待的。

**实现方式**：A → 父（编排器）→ B 的中转路由。防死锁通过 `correlation_id` + `deadline` 分级恢复：单条超时重试 ≤2；同 Agent 同链路 ≥3 次强制终止；工作流超时降级审批。

**设计要点**：流水线交接（文件为主）与即时协商（消息为主）是**两种不同的交互模式**，前者走 durable 通道，后者走 transient 通道。

### 5.3 可视化激活状态（G3）：状态机 + Event 广播

**约束**：节点状态是**有限状态机**的显式状态，不是隐式的。

**实现方式**：Host 维护节点状态 `idle/pending/running/waiting/done/error`，通过 Event 广播到 Client，画布实时染色。先只读看板（MVP-4），后拖拽编辑器（MVP-5）。

**与 RunLedger 的关系**：节点状态是**当前快照**（来自 State），Event 流是**历史轨迹**（来自 RunLedger）。画布同时消费两者——快照决定当前颜色，轨迹决定动画路径。


## 六、质量验证模型（双层）

系统需要在两个层面验证质量，二者不可互相替代：

| 层面 | 验证什么 | 怎么验证 | 何时落地 |
|---|---|---|---|
| **结构覆盖** | 工作流是否被完整执行——允许工具被调用、委托义务被履行、限制工具被拒绝 | StateGraph 的路由/条件边/熔断都是**纯函数**，用 BDD + mock 隔离 LLM 做确定性测试（零 Token、毫秒级） | **MVP-2**（不等 MVP-6） |
| **语义评估** | 输出质量是否达标 | LLM-judge，R8 对立角色对抗评审 | MVP-6 |

**为什么结构覆盖要提前到 MVP-2**：StateGraph 引擎的路由逻辑是**确定性的**，不需要真实 LLM 调用就能验证。等到 MVP-6 才做"全套门禁"意味着 MVP-2 到 MVP-5 期间，路由错误只能靠人工发现。提前用 mock 测试覆盖，成本极低，收益极高。


## 七、演进路径（六个 MVP）

**演进原则**：每个 MVP 有独立的**质变点**和**门禁**，前一阶段的产物是后一阶段的基础。

| MVP | 名称 | 质变点 | 门禁 |
|---|---|---|---|
| 0 | 角色资产 | R1-R10 skill + 横切纪律 | 已过 |
| 1 | 单链脚本验证 | 打通「角色=provider+persona」 | 多角色顺序跑通真实小任务 |
| **2** | **自研 StateGraph 引擎** | **工作流可配置（图 DSL + 循环）** | 含循环 DSL 跑通 + 熔断双生效 + 路由确定性测试 + 热重载无泄漏 |
| 3 | 状态+交接+消息+恢复 | 可持久化/可恢复/分账/防死锁 | 中断可恢复 + 交接可追溯 + 按角色分账 |
| 4 | 只读激活看板 | 状态可视化 | 全程图节点实时染色 |
| 5 | 角色导入+画布连边 | 零代码自定义团队（G6） | 零代码搭团队跑通 + 画布产物=合法 DSL |
| 6 | 打磨 | 生产可用 | 全套门禁 + 社区可分发 |

**MVP-2 是质变点**：从"一堆 skill"到"编排工具"的跨越发生在这里。MVP-1 用 workflowEngine 临时验证角色协作，但那是**脚本式**的——表达条件边/循环/精确节点状态很别扭。MVP-2 的 StateGraph 才是**图范式**。

**MVP 之间的依赖关系**：

```
MVP-0（角色资产）
    ↓
MVP-1（单链验证）← 验证角色协作可行性
    ↓
MVP-2（StateGraph 引擎）← 质变点，工作流可配置
    ↓
MVP-3（状态+交接+消息+恢复）← 可持久化，为可视化打数据基础
    ↓
MVP-4（只读看板）← 状态可视化
    ↓
MVP-5（角色导入+画布）← 零代码自定义
    ↓
MVP-6（打磨）← 生产可用
```

**每阶段对应的核心交付**：

| MVP | 核心交付 | 对应契约 |
|---|---|---|
| 1 | 角色 Provider 编译器 + workflowEngine 脚本 | `04` §4.4 角色 YAML schema |
| 2 | 图 DSL Schema + StateGraph 引擎 + checkpoint 契约 + 观察者 L1 | `04` §4.1/§4.2 |
| 3 | 消息总线 + RunLedger + 生命周期 + Token 熔断 + 观察者 L2 | `04` §4.3/§4.4/§4.5 |
| 4 | 事件流 + 图渲染 + 审批面板 + 观察者信号可视化 | `04` §4.1 metadata |
| 5 | 画布编辑器 + Gallery + 自定义节点 | `04` §4.1 GraphDefinitionSpec |
| 6 | 恢复加固 + 记忆压缩 + 对抗评审 + 社区分发 | `04` §5 Token 优化 |


## 八、决策点状态（已收敛）

以下决策经过多轮探测与评审已收敛，不再作为开放问题：

| 决策点 | 结论 | 理由 |
|---|---|---|
| 编排引擎 | ✅ 自研 StateGraph | workflowEngine 是脚本式，表达条件边/循环别扭 |
| 运行时底座 | ✅ 分层复用：subagents + 自建 | 不依赖 experimental agentTeams（不支持循环 + 实测不兼容） |
| 角色定义 | ✅ YAML 元数据 + `system_prompt_ref` | traits 是元数据，Prompt 来自 skill |
| 开发路径 | ✅ 纯 Host CLI 先行 | MVP-1/2 不碰 UI，先验证编排逻辑 |
| 编排 vs 可视化顺序 | ✅ 编排前置于可视化 | 没有编排逻辑，可视化只是空壳 |
| Token 熔断 | ✅ 复用官方 + 社区 | 不自研，`@deepseek-ai/dsh-agent-budget` + `dsh-discipline-guard` |
| 记忆隔离 | ✅ 复用 subagent | `inheritsParentContext=false` 已提供，不自研 |
| **Task 建模** | ✅ **Agent 拆解出 Task，Task 树自然形成** | 不是"预先定义 Task 列表再指派给 Agent" |

**仍有待 PM 裁决的**：并发全局上限是否接受当前 DSH 结构性限制（自建引擎层计数）。


## 九、风险（设计层面的关注点）

| 风险 | 本质 | 缓解设计 |
|---|---|---|
| **StateGraph 自研复杂度** | 原子合并 + 并发安全 + 冲突策略 | MVP-2 只做 seq+cond+loop，parallel 后推 |
| **冷恢复延迟** | subagent 从持久化 Session 恢复的延迟 | 生命周期 resident/on-demand/hybrid + 10s SLA 降级人工 |
| **循环失控 / 成本爆炸** | 未控 Agent 循环可达月 $10K 级 | 迭代熔断(25) + 硬 Token 预算 + 人工审批节点 |
| **记忆/上下文膨胀** | 每轮对话累积 | handoff 精简 + `art://` 引用 + 滑动窗口摘要 |
| **Task 拆解失控** | Agent 过度拆解导致协调开销爆炸 | `max_iterations` + Token 预算 + 拆解深度限制 |
| **并发失控** | dsh-subagent 无进程级并发闸 | 多层防护：Provider 层 + Agent Loop 层 + 引擎层 |
| **Cordis 热重载泄漏** | 非 effect 管理的资源在 HMR 时泄漏 | 所有非 Cordis 资源必须 `ctx.effect()` 包装 |
| **Messages 协议 notice 毒化** | 跨版本升级后旧会话不可用 | 不依赖 settlement notice 恢复，用 RunLedger 重建 |
| **Agent 治理缺失** | Agent 是"特权内部人员" | 短期凭证 + 记忆防投毒 + 执行前验证 + `toolFilter` |
| **可观测性不足** | 无法调试多 Agent 协作 | OpenTelemetry 逐节点插桩，`trace_id` 贯穿全链 |
| **工作区卫生退化** | 多角色产出混杂 | 每角色独立产出目录 + 卫生检查 |

**风险与 MVP 的对应**：多数风险在 MVP-2/MVP-3 集中处理（并发、热重载、记忆膨胀、Task 拆解），少数在 MVP-6 打磨（对抗评审、记忆压缩）。风险缓解措施在 `04` §7 有完整列表。

## 十一、总结

**本工具的设计哲学**：把工作流从"人肉配置"升级为"图 DSL + 自动调度运行时"。系统的核心动力是 **Agent 拆解 Task**——用户需求产生根 Task，Agent 执行 Task 时按图 DSL 的协作协议拆解出子 Task，指派给下游 Agent，Task 树自然形成。

六个对象分三层组织：
- **协作层**：Workflow（协作协议）+ Agent（执行者）
- **执行层**：Task（工作单元，由 Agent 拆解产生）
- **状态层**：State（当前快照）+ Memory（Agent 独立记忆）+ RunLedger（历史轨迹）

三条命门（记忆纯洁性/定向对话/状态可视化）是不可越过的约束；双层质量验证（结构覆盖 + 语义评估）保证正确性；六个 MVP 渐进式演进，在 **MVP-2（自研 StateGraph）** 完成从"一堆 skill"到"编排工具"的质变。
